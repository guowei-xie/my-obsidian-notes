# 方法论 · 可迁移模式

> 子笔记 · 回 [[00-总览]]。本篇抽象「拿掉 SalesCopilot 这个壳、还能指导我做别的项目」的套路。每条都锚定源码证据。事实与结构见 [[01-四阶段管线与编排]]、[[02-知识图谱与经验模型]]。

## 元命题：LLM 管「理解与生成」，程序管「一致性、幂等、结构」

这个项目最核心的可迁移思想：**在一条 LLM 深度参与的管线里，凡是「需要跨样本一致、可累积、可回溯」的东西，都不要交给 LLM 直接决定，而是让 LLM 产出「候选/语义」，再由确定性程序收敛成「事实/结构」。** 下面五个模式都是这条元命题的具体落法。

## 模式 1 · 用「全局受控词表」驯服 LLM 的用词漂移

**问题**：让 LLM 自由打标签，同一个概念每次措辞都不同（「价格敏感」/「对价格犹豫」/「嫌贵」），标签无法聚合、图谱无法检索。

**做法**（[[01-四阶段管线与编排]] Stage 3）：
1. 每次任务先从「事实源」（这里是 Neo4j）读一份**当前全局标签快照**，与内置默认词表合并成不可变的 `TagCatalog`；
2. 把词表注入 prompt，要求**沿用优先**；
3. 确需新词时 LLM 必须在专门字段里**显式声明**（带 `reason` + `evidence` + 极性），空泛词（"其他""话题"）一律拒；
4. 程序端**校验**：用了快照外且未声明的标签 → 带错误清单**自动重试一次**；
5. 声明并落库的新标签成为下次快照的一部分——**词表随使用自我生长，但始终受控**。

**为什么值得搬**：任何「LLM 抽取要进结构化库并长期累积」的场景（实体标准化、意图分类、标签体系、审计维度）都适用。它把「开放生成」变成「受约束的开放生成」——既不僵死也不失控。证据：`tag_catalog.py` 的 `build_tag_catalog`/`validate_distillation_labels`、`distill.py` 的 `_call_with_label_validation`。

## 模式 2 · 结构化字段做「零 LLM 成本」去重

**问题**：判断两条萃取结果是不是「同一回事」，直觉会想上 embedding 或再调一次 LLM——贵、慢、不确定。

**做法**（`ingest.py` `DeduplicatorState`）：把去重降维成**结构化键 + 集合相似度**——`(approach_id, from_stage, to_stage)` 分桶，桶内用 `factors_addressed` 的 **Jaccard 相似度**判近似，超阈值的相似经验累计到上限（默认 3）就丢弃。**完全复用上游归一化结果 + 结构字段，零额外调用。**

**关键设计取舍**：保留最多 N 条相似经验（而非仅 1 条）——因为「不同销售的话术风格、不同用户的反应」本身就是有价值的证据多样性。去重是「限流」不是「唯一化」。且 `Approach.example_count` 在归一化时（去重闸门之前）就已自增，**被去重丢弃的经验仍忠实计入证据量**——统计口径与图谱膨胀解耦。

**为什么值得搬**：当你的对象已经有了好的结构化维度，别急着上向量。先问「能不能用已有字段拼一个够用的相似度」，常常又快又可解释。

## 模式 3 · 确定性 ID + 预占位 MERGE = 天然幂等 + 可断点续跑

**问题**：长管线中途失败/暂停后重跑，怎么不产生重复数据、不重复累加计数？

**做法**：
- **确定性 ID**：`EXP-{sample_id}-{idx}` 由输入唯一决定，重跑必然命中同一节点（`MERGE` 幂等）。
- **预占位探测新建**（`reserve_experience`）：`MERGE` 时写一个一次性 marker，用「marker 是否等于本次值」判断这条是不是**本次真正新建**；只有新建的才继续写边——一举两得：① 免掉逐条 `MATCH...LIMIT 1` 的 N+1 存在性检查；② 防止重跑对累加型边计数（`evidence_count`）重复 +1。
- **DB 层唯一键 + upsert**：`(task_id, conversation_id)` / `(task_id, experience_id)` 唯一键让各阶段中间结果可安全重入。
- **阶段级短路**：`run_resume` 靠「查 DB 已产物计数」跳过已完成阶段，从断点续跑。

**为什么值得搬**：这是把「幂等」从口号落成机制的一整套配方。任何「可能重跑的批处理/ETL/图谱构建」都能照抄：ID 由输入派生 + 写入用 MERGE/upsert + 用「本次是否新建」把「累加副作用」和「幂等主体」分开。证据：`neo4j_writer.reserve_experience`、`orchestrator.run_resume`、`db/schema.py` 唯一键。

## 模式 4 · 图谱的「边」由决策矩阵生成，而非让 LLM 直接吐拓扑

**问题**（原项目的真实教训）：让 LLM 同时产「场景全景因素」和「本条经验处理的因素」，两者不一致 → 图谱里一堆没有边的孤立 Factor 节点。

**做法**（两端夹击）：
- **语义端**：prompt 里把 `context 因素`（全景）与 `factors_addressed`（实际处理）的关系约束成「子集」，从源头减少不一致。
- **结构端**：**Factor 节点只从 `factors_addressed` 建**，context 因素只作 Experience 属性存；边则由 `edge_planner` 的**「经验类型 → 建哪些边」决策矩阵**确定性生成（见 [[02-知识图谱与经验模型]] 的矩阵表）。LLM 从不直接决定图的拓扑，只提供填充边的语义。

**为什么值得搬**：知识图谱构建里，**「实体/关系的语义」适合 LLM，「图的拓扑规则」适合确定性代码**。把这两层分开，既避免孤立节点/悬空边，又让图谱结构可预测、可校验。这是「LLM 产料、规则成图」的典范。

## 模式 5 · 分层防御 + 单条失败不阻断整批

**做法**：
- **按「谁消费」定解析严格度**：LLM→LLM 环节（Stage 2 的 key_moments 传给 Stage 3）**宽容原样传递**，非标准 JSON 也无妨，下游 LLM 能理解；LLM→程序环节（Stage 3→Stage 4）**严格 JSON 解析 + 强校验**，失败即标记跳过。
- **三级容错**：任务级（配置/DB/Neo4j 连接失败 → `failed`）／样本级（API 无数据 → 跳过继续）／经验级（解析/校验失败 → 记 `skipped/failed` 继续下一条）。
- **失败留痕**：LLM 调用失败写 `_call_error` 占位行而非静默丢弃，可追溯。
- **降级而非中断**：Approach 归一化任何异常都降级为「建新方法」，绝不阻断主流程。

**为什么值得搬**：面对「LLM 输出不可靠 + 批量长任务」的组合，正确姿势是**把容错做成分层策略**：明确每个边界「失败了该退到哪一级」，而不是一个 try/except 兜底。证据：`orchestrator.run` 的异常分层、各 Stage 的占位行写法、`approach_normalizer` 的降级逻辑。
