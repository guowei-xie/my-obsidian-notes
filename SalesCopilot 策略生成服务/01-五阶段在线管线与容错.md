# 五阶段在线管线与容错

> 子笔记 · 回链 [[00-总览]]。姊妹篇：[[02-用户背景模块（Stage 2）]] · [[03-图谱检索·数据契约·Prompt]] · [[04-方法论·可迁移模式]]
> 以代码 `@4aaa067` 为准。

## 编排器：Orchestrator.run()

`pipeline/orchestrator.py` 的 `Orchestrator` 在构造时一次性加载三处 LLM 配置（intent/strategy/history_summary）与图谱检索参数（top_k/advance_limit/resolve_limit 各默认 8），持有共享的 `hetao` / `neo4j` / `catalog`。`run(req)` 顺序执行五阶段，每段用 `stage_timer` 记录耗时到 `latency_ms`，最终组装 `StrategyResponse`（5 顶层字段 + `debug_meta`）。

关键点：**编排器本身不做超时熔断**。`stage_timer`（`utils/timing.py`）只是量耗时的上下文管理器，`try/finally` 记 `perf_counter` 差值——没有任何 `timeout` 逻辑。真正的超时只有一处：路由层 `asyncio.wait_for(..., 90s)`（见下文「超时」）。

## 五阶段逐段行为

### Stage 1 · Fetch（拉对话）
`hetao.fetch_dialogue(user_id, counselor_id, moment)` → `(fulltext, msg_count)`。失败（网络/HTTP）抛 `StageError("fetch", ..., http_code=502)`。数据契约（call/wechat 解析、时区归一、moment 截断）见 [[03-图谱检索·数据契约·Prompt]]。

- **降级点**：`msg_count == 0` **不报错**，只 `warnings.append("no_dialogue")` + 日志，继续往下。

### Stage 2 · Profile（用户背景）
- `req.skip_user_profile == True`：直接 `user_profile = {}`，`latency_ms["profile"]=0`，记 `warnings.append("skip_user_profile")`。
- 否则调 `fetch_user_profile(config_path, user_id, counselor_id, catalog=catalog_snap, history_summary_llm=...)`——完整订单背景模块，**内部自己吞异常返回 `{}`**（不抛到编排器）。深挖见 [[02-用户背景模块（Stage 2）]]。

### Stage 3 · Intent（意向分析）
- **若 Stage 1 无对话（msg_count==0）**：跳过 LLM，直接构造 `IntentAnalysis(intent_stage="S1", intent_reason="未检索到任何对话记录", 空因素)`，`latency_ms["intent"]=0`。
- 否则调 `run_intent_analysis(轻量 llm, catalog, user_profile, dialogue_text)`；失败抛 `StageError("intent", ..., 500)`。逻辑/prompt 见 [[03-图谱检索·数据契约·Prompt]]。

### Stage 4 · Graph（图谱检索）
`run_graph_retrieval(neo4j, intent_stage, positive_factors, negative_factors, limits...)`。失败抛 `StageError("graph", ..., 500)`。

- **降级点**：结果为空 → `warnings.append("no_experience_matched")`，继续（Stage 5 prompt 会据此把 confidence 打 low）。
- **两查询并行**：`ThreadPoolExecutor(max_workers=2)` 跑 advance / resolve；**单个查询内部异常被 catch 成空列表**（`f_adv.result()` 包 try），不会让整个 Stage 4 失败——只有连不上等更外层异常才抛 StageError。
- **特殊路径**：`intent_stage=="S4"` 跳过 advance；`negative_factors==[]` 跳过 resolve。合并按 `approach_id` 去重（advance 来源优先）→ `example_count` 倒序 → 截 Top-K。详见 [[03-图谱检索·数据契约·Prompt]]。

### Stage 5 · Strategy（策略生成）
`run_strategy_generation(重量 llm, intent, user_profile, moment_iso, dialogue_text, experiences, top_k)` → `(StrategyCard, refs, latency)`。失败抛 `StageError("strategy", ..., 500)`。

- **兜底校验**：`current_stage`/`target_stage` 非法回退（→ intent 阶段 / → current）、`confidence` 非法回退 `medium`、`actions` 逐条容错解析并按 priority 排序、`topic_flow` 兼容 LLM 输出的 list 或 `→` 分隔 string、对话过长尾部保留 6000 字符（最近的最相关）。

## 容错哲学：抛错 vs 降级，看依赖性质

这是本管线最值得记的设计——**不是所有失败都同等对待**：

| 情况 | 处理 | 理由 |
|---|---|---|
| hetao API 失败 | 抛 502 | 硬依赖，拉不到对话就没有输入 |
| Stage 3/4/5 LLM/Neo4j 异常 | 抛 500 | 核心链路断了，宁可失败不造伪产物 |
| 整体 > 90s | 抛 504 | 路由层 `asyncio.wait_for` |
| 对话为空 | 降级：意向直接 S1，跳过 Stage3 | 无对话是合法业务态（沉默用户），不是错误 |
| 图谱无命中 | 降级：经验列表 []，confidence=low | 缺经验仍能给通用建议 |
| user_profile 拉取异常 | 降级：`{}` | 背景是增强信息，缺了不致命 |
| advance/resolve 单查询异常 | 降级：该查询空列表 | 另一路仍可能有结果 |

对照 PRD §9「失败即失败，不构造伪造产物」——代码是**分层**贯彻：核心链路严格失败，边缘信息缺失优雅降级，用 `debug_meta.warnings` 把降级痕迹透明地回传。（注意：PRD 说无对话返回 422，代码实际是降级 S1，见 [[00-总览]] 差异清单。）

## 超时与错误码

**超时**：仅路由层 `post_strategy` 用 `asyncio.wait_for(asyncio.to_thread(orchestrator.run, req), timeout=overall_s)`，默认 90s，超时抛 504。`orchestrator.run` 是同步阻塞代码，靠 `to_thread` 丢线程池不卡事件循环。**per-stage 超时（PRD §8 的 fetch 25s/intent 30s/…）在代码里不存在**。

**错误码映射**（`api/routes.py`）：

| HTTP | 触发 |
|---|---|
| 200 | 成功 |
| 422 | Pydantic 请求体校验失败（FastAPI 默认） |
| 502 | Stage 1 hetao 失败（StageError.http_code） |
| 500 | Stage 3/4/5 失败，或未捕获异常 |
| 503 | orchestrator/catalog 未初始化（config.ini 缺失的占位模式） |
| 504 | 整体 > overall_s |

`StageError(stage, message, http_code)` 是自定义异常，携带 stage 标签供路由精准映射；路由把 `{stage, message}` 放进 `HTTPException.detail`。

## 旁路异步落库

响应生成后，若 `strategy_storage` 开启且 `[mysql]` 配全：

```python
async def _persist_mysql(): ...   # save_strategy_response(...)
asyncio.create_task(_persist_mysql())   # 不 await
```

**关键**：`create_task` 后立即 `return JSONResponse` —— 落库是旁路，不阻塞响应；落库失败只记日志（`_persist_mysql` 内部 try/except），不影响已返回给用户的策略。落库默认**开启**（`strategy_storage_override is None → True`），可用 `--no-storage` 关。结果表结构（`strategy_results`：user_id/counselor_id/moment_iso/intent_stage/response_json/created_at，首次写入自动建表）见 `storage/mysql_result_store.py`。

## 三种运行入口，一套编排

| 入口 | 文件 | 场景 |
|---|---|---|
| 在线 API | `src/main.py` → `POST /strategy` | 生产实时 |
| 单条脚本 | `scripts/run_strategy_persist_once.py` | 调试单个 user/counselor/date |
| 批量脚本 | `scripts/batch_strategy_from_mid_table.py`、`run_strategy_sql_mid_with_profile.py` | 从订单宽表拉列表逐条跑并落库 |

三者都调 `build_orchestrator(config_path)` 拿同一个 `Orchestrator`——**在线与离线走完全一致的管线代码**，只是驱动方式和 moment 取法不同（脚本按日期取当日 `23:59:59+08:00`）。这保证批量回填和线上产物同源可比。

## 配置与运行

- 启动：`python src/main.py`（开发）/ `uvicorn src.main:app --host 0.0.0.0 --port 8100 --workers 1`（生产）。
- **workers 必须为 1**：catalog 缓存与 Neo4j driver 是 lifespan 建的进程内单例，多 worker 会重复建连且缓存不共享。并发靠多实例 + 反代（README「部署提示」）。
- CLI 参数（`main.py` argparse，写入 `utils/app_runtime` 全局态供 lifespan 读）：
  - `--storage / --no-storage`：是否落库，默认开。
  - `--database mysql|hive`：结果看板取数 + Stage 2 订单宽表的数据源，默认 mysql。
- config.ini 关键段：`[server]`、`[hetao_data]`、`[neo4j]`、`[mysql]`/`[hive]`、`[catalog] ttl_seconds`、`[graph_query] top_k/advance_limit/resolve_limit`、`[stage_timeout] overall_s`、`[llm.default]` + `[llm.intent]`/`[llm.strategy]`/`[llm.history_summary]`。LLM 分阶段配置见 [[03-图谱检索·数据契约·Prompt]]。
