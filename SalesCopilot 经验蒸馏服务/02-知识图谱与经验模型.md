# 知识图谱与经验模型

> 子笔记 · 回 [[00-总览]]。本篇是**图谱的权威 schema 描述 + 经验字段字典**。下游写 Cypher 请以此为准（仓库 `docs/product_spec.md` 的 schema 已过时）。管线怎么把这些填出来见 [[01-四阶段管线与编排]]。

## 意向阶段 S0–S4（核心坐标系）

整个图谱以「用户购买意向」的 5 级阶梯为骨架（`prompts/experience_distillation_v1/system.txt`）：

| 阶段 | 名称 | 判定标准 |
|---|---|---|
| S0 | 暂缓/流失 | 明确拒绝信号，或消极因素压倒性主导 |
| S1 | 沉默用户 | 无话题交集，或话题极少且无因素信号 |
| S2 | 需求模糊 | 有话题交集、有弱积极因素，但未形成明确方向 |
| S3 | 需求明确 | 多话题下积极因素主导，主动表达需求 |
| S4 | 强购买意愿 | 出现强购买信号（询价/约课/问报名） |

每条经验携带 `from_stage → to_stage`，`to ≥ from`（校验强制）。图谱里 5 个 `IntentStage` 节点在 schema 初始化时 MERGE 出来（`UNWIND ['S0'..'S4']`）。

## 经验数据模型（Experience）

`src/models/experience.py`。一条经验是 LLM 从单个关键时刻抽象出的结构，`experience_id = EXP-{sample_id}-{idx}`。字段字典：

| 分组 | 字段 | 含义 |
|---|---|---|
| — | `experience_type` | 5 类之一（见下） |
| `context` | `description` | 抽象后的适用情境（非特定用户） |
| | `intent_stage` / `intent_stage_reason` | 该时刻用户所处阶段 + 判定依据 |
| | `positive_factors` / `negative_factors` | 该情境的正/负因素（场景全景） |
| `judgment` | `what` / `why_effective` / `alternative_avoided?` | 销售做了什么 / 为何有效 / 刻意避免了什么 |
| `execution` | `approach` / `how` | 方法一句话概括（供归一化）/ 具体怎么做 |
| `effect` | `user_response_change` | 用户反应如何变化 |
| `evidence` | `before` / `action` / `after` | 证据三段原文（**缺一不可**）；可选 `contrast_action`/`contrast_after` |
| `retrieval_tags` | `from_stage` / `to_stage` | 适用的起始/目标阶段 |
| | `factors_addressed` | **本条经验实际化解/利用的因素**（context 因素的子集） |
| | `topics` / `applicable_segments` | 涉及话题 / 适用用户群特征 |

**5 种经验类型**：

| 类型 | 标签 | 判定 |
|---|---|---|
| 意向推进 | `intent_advance` | 意向阶段正向变化 |
| 阻塞化解 | `blocker_resolve` | 顾虑/异议被化解或弱化 |
| 信号捕捉 | `signal_capture` | 捕捉积极信号并有效放大 |
| 节奏把控 | `pacing` | 时机/顺序上的正确选择 |
| 信息承接 | `context_leverage` | 利用已有背景信息增强针对性 |

**`context 因素` vs `factors_addressed` 的关键区分**（原项目孤立节点的根因，本项目在 prompt 层约束）：`context.*_factors` 是「场景里存在的因素全景」，`factors_addressed` 是「这条经验真正处理的因素」，后者是前者的**子集或等集**，不允许出现 context 里没有的因素。→ 图谱构建端据此只从 `factors_addressed` 建 Factor 节点，context 因素仅作 Experience 属性存储，从而每个 Factor 节点天然有边。

**强校验**（`validate_experience`）：`experience_type` 合法 + `from/to ∈ {S0..S4}` + `to ≥ from` + evidence 三段非空 + `execution.approach` 非空；任一不过 → 该经验 skipped。

## Factor / Topic 标签治理

- **默认因素极性表**（`factor_classifier.DEFAULT_FACTOR_POLARITY`，冷启动兜底）：
  - 正：学习兴趣、目标明确、主动询价、主动约课、社交背书、体验认可、竞赛需求、时间窗口明确
  - 负：价格敏感、决策权模糊、时间冲突、效果怀疑、兴趣不足、竞品倾向、年龄顾虑、外部条件
- **标签快照**（`tag_catalog.build_tag_catalog`）：每任务把 Neo4j 现有 `Factor` 与默认表**合并去重排序**成 `TagCatalog`（正因素、负因素、话题三个不可变元组）。Neo4j 里的极性覆盖默认表。
- **极性归属**（`classify_factors`）：某因素的极性判定优先看当前经验 `context` 的正/负列表，再查全局/默认极性表兜底（**兜底默认判为 negative**）。
- **新标签闭环**：LLM 新建的 Factor/Topic 经 Stage 3 校验（须举证）→ Stage 4 成功写入 Neo4j → 成为后续任务快照的一部分。标签库随使用自我生长，但受「沿用优先 + 举证 + 拒空泛」三重约束。

## Neo4j 图谱 Schema（以代码为准）

### 节点（6 类）

`neo4j_writer.init_schema` 建的唯一约束即权威节点清单：

| 节点 | 唯一键 | 关键属性 |
|---|---|---|
| `IntentStage` | `name` | S0–S4，初始化时 MERGE |
| `Factor` | `(name, polarity)` 复合唯一 | `name`、`polarity∈{positive,negative}` |
| `Approach` | `approach_id` | `name`、`description`、`example_count`、`created_at`、`last_updated` |
| `Experience` | `experience_id` | 经验全字段平铺为属性（含 `from_stage`/`to_stage`/`factors_addressed`/`topics` 等） |
| `Topic` | `name` | `name` |
| `Counter` | `name` | `approach_seq`（生成 `APR-{seq:04d}` 的原子自增计数器） |

> **没有 `Dialogue` 节点**——它在 commit `924e436 fix: remove Dialogue node from graph build` 被移除。

### 边（7 类）— 注意方向

以 `write_edges` 的 Cypher 为准（这是与设计稿分歧最大处）：

| 边 | 方向（起→终） | 属性 | 语义 |
|---|---|---|---|
| `TRANSITION` | `IntentStage → IntentStage` | `evidence_count`、`success_rate`、`created_at`、`last_updated` | 意向阶段跃迁 |
| `BLOCKS` | `Factor(negative) → IntentStage` | `from_stage`、`evidence_count`、`block_strength` | 负因素阻碍某跃迁 |
| `DRIVES` | `Factor(positive) → IntentStage` | `from_stage`、`evidence_count`、`drive_strength` | 正因素推动某跃迁 |
| `RESOLVES` | `Approach → Factor(negative)` | `for_from_stage`、`for_to_stage`、`evidence_count` | 方法化解某负因素 |
| `LEVERAGES` | `Approach → Factor(positive)` | `for_from_stage`、`for_to_stage`、`evidence_count` | 方法利用某正因素 |
| `EVIDENCE_OF` | `Experience → Approach` | — | 经验是方法的实例证据 |
| `INVOLVES` | `Experience → Topic` | — | 经验涉及某话题 |

关键点：**`BLOCKS`/`DRIVES` 连的是 Factor→IntentStage（不是 Experience→Factor）；`RESOLVES`/`LEVERAGES` 连的是 Approach→Factor**。经验与因素的关联通过 `EVIDENCE_OF`→Approach 以及 Experience 节点上的 `factors_addressed` 属性间接体现。

### 边规划决策矩阵

`edge_planner.plan_edges` 按经验类型决定建哪些边（因素来自 `classify_factors` 的正/负分组）：

| 类型 | TRANSITION | BLOCKS(负F→stage) | DRIVES(正F→stage) | RESOLVES(A→负F) | LEVERAGES(A→正F) | EVIDENCE_OF |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| `intent_advance` | ✓ | — | ✓ | — | ✓ | ✓ |
| `blocker_resolve` | ✓ | ✓ | — | ✓ | — | ✓ |
| `signal_capture` | ✓ | — | ✓ | — | ✓ | ✓ |
| `pacing` | 仅 from≠to | — | — | — | — | ✓ |
| `context_leverage` | ✓ | ✓ | ✓ | — | ✓ | ✓ |

`INVOLVES` 对每个 topic 各建一条，独立于类型。

### 派生指标（批末重算，`recompute_derived_metrics`）

- `TRANSITION.success_rate` = 本边 `evidence_count` ÷ 该起点 `IntentStage` 所有出向 TRANSITION 的 `evidence_count` 之和（该阶段流向各下一阶段的占比）。
- `BLOCKS.block_strength` = 本边 `evidence_count` ÷ 对应 `from_stage→to_stage` 的 `TRANSITION.evidence_count`。
- `DRIVES.drive_strength` = 同上口径（正因素版）。
- 边计数（`evidence_count`）在 `write_edges` 里 `ON CREATE=1 / ON MATCH +1` 累加——配合 Stage 4 的预占位「只对新建经验写边」，避免重跑导致重复累加。

## Approach 归一化

`approach_normalizer.py`：先用 `fetch_approach_catalog` 按相关性检索候选（同路径+同类型+因素重叠 > 同路径+同类型 > 邻近路径+同类型），候选为空**直接建新**（省一次 LLM）；否则 LLM 判：

- `matched` → 复用该 `approach_id`，`example_count += 1`；ID 不存在则降级 new。
- `revise` → 用 LLM 给的新名/描述更新该 Approach，`example_count += 1`；ID 不存在则降级 new。
- `new` → `allocate_new_approach_id()` 原子自增 Counter 生成 `APR-{seq:04d}`，建新节点。
- 任何 LLM 异常都降级 new——归一化永不阻断主流程。

## 设计稿 vs 代码（差异清单）

`docs/product_spec.md` 是早期设计稿，下列已与代码不符，**以代码/本笔记为准**：

| 设计稿说法 | 代码实际 |
|---|---|
| 有 `Dialogue` 节点 + `FROM_DIALOGUE` 边（做路径分析） | 已删除；路径分析靠 `sample_id` 属性 + 同 sample 的多经验 |
| `BLOCKS/DRIVES: Experience → Factor` | `Factor → IntentStage`（带 `from_stage`） |
| `RESOLVES/LEVERAGES: Experience → Factor` | `Approach → Factor` |
| ingestion 状态 `done/deduplicated` | 实际 `ok/skipped/failed`（去重记 skipped + `dedup_dropped`） |
| MySQL 表名 `tasks/conversations/...`、字段 `fulltext`、`JSON` 类型 | 实际 `distill_tasks/distill_conversations/...`、`dialogue_text`、`MEDIUMTEXT` |
| summary 字段 `conversations_fetched/...` | README 版为准：`conversations/retained_key_moments/experiences_extracted/ingested_ok/ingested_failed/ingested_skipped` |
| Experience ID 示例 `EXP-456-123-0` | 规则 `EXP-{sample_id}-{idx}`，其中 `sample_id={user_id}-{counselor_id}` |
