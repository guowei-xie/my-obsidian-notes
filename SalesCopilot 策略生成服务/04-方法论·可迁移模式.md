# 方法论 · 可迁移模式

> 子笔记 · 回链 [[00-总览]]。证据散见 [[01-五阶段在线管线与容错]] · [[02-用户背景模块（Stage 2）]] · [[03-图谱检索·数据契约·Prompt]]。
> 这里只写**能搬到别处用的套路**，不复述功能。

## 1. 知识图谱的「读写分离两半」

**模式**：把一个"沉淀知识 → 应用知识"的系统，拆成**离线写侧**和**在线读侧**两个独立服务，共享 schema 与坐标系，各自优化。

- 写侧（[[SalesCopilot 经验蒸馏服务/00-总览|经验蒸馏服务]]）：批量、可断点续跑、追求图谱质量与幂等，把成功对话蒸馏进 Neo4j。
- 读侧（本服务）：实时、低延迟、只读，把图谱知识落到具体用户身上出决策。
- 共享：Neo4j schema（Experience/Approach/Factor/Topic、`EVIDENCE_OF` 边、`experience_type` 取值）、S0-S4 意向坐标系、hetao 对话 API 血统。

**为什么值得搬**：读写诉求根本冲突——写侧要吞吐和一致性、读侧要延迟和可用性。捏在一个服务里会互相拖累。分开后，图谱成了两者之间**稳定的契约面**，各自能独立演进、独立扩缩容。任何"离线构建知识库 + 在线检索应用"的系统（推荐、RAG、风控规则库）都适用。副作用：schema 是跨服务隐式契约，改字段要两边同步——本服务只读且 schema 以写侧为准，就是在认这个约束。

## 2. 一份受控词表，约束全部 LLM 用词

**模式**：系统里每一处让 LLM 产标签/分类的地方，都注入**同一份从权威源（这里是 Neo4j）读来的受控词表**，并在**程序端逐字段过滤**掉词表外的输出。

- 本服务三处 LLM 有两处（意向分析、历史摘要）吃 catalog 快照；prompt 里"必须逐字用清单内字面量、不自造"，程序端 `_normalize_*` 再兜一道过滤。
- 与写侧蒸馏服务完全同源的纪律——保证**同一个"价格敏感"因素，在写入时、在线判意向时、在检索匹配时是同一个字面量**，否则 Stage 4 的 `CONTAINS` 匹配就会漏。

**可迁移点**：只要有"多处 LLM 调用要产出可互相 JOIN 的标签"，就该有一份中心词表 + 双重保险（prompt 约束 + 程序过滤）。**别信 prompt 单独能管住用词漂移**——LLM 会创造性发挥，程序端过滤是最后防线。词表放在数据源侧（而非硬编码）让它能随业务演进。

## 3. 分阶段异构 LLM：按环节诉求选模型

**模式**：一条链路里不同环节对"延迟 vs 质量"诉求不同，就给每个环节**独立配模型**，并设一个 default 兜底。

- 意向分析/摘要 → qwen-plus（轻、快、要确定性 temp=0）；策略生成 → deepseek-r1（重、会推理、质量优先）。
- 实现上：`[llm.<stage>]` 覆盖 `[llm.default]`，空值视为未设置继续 fall through——配置层就能调模型，不改代码。

**可迁移点**：多步 LLM 管线不该一个模型跑到底。前置的抽取/分类用便宜快模型、终端的生成/推理用贵好模型，是**成本与质量的帕累托改进**。关键是把模型选择做成配置而非硬编码，方便按线上表现调。

## 4. 按依赖性质分层容错：抛错 vs 降级

**模式**：不搞"要么全 try/except 吞掉、要么全抛"，而是**按依赖是否致命分类**处理。

| 类别 | 例子 | 处理 |
|---|---|---|
| 硬依赖（缺了没法算） | hetao 拉对话、核心 LLM、Neo4j | 抛错映射 HTTP，不造伪产物 |
| 软信息（缺了能降级） | 对话为空、图谱无命中、用户背景、单路查询 | 降级继续，记 `warnings` 透明回传 |

见 [[01-五阶段在线管线与容错]] 的容错表。"对话为空→意向直接 S1 而非报错"是典型——**空是合法业务态（沉默用户），不是异常**。

**可迁移点**：容错的粒度应该匹配业务语义，不是技术上的"能不能 try"。区分"这个失败让结果无意义"（抛）和"这个失败让结果变差但仍有用"（降级），并用结构化 `warnings`/`debug_meta` 让调用方知道拿到的是不是降级产物——**降级要透明，不能静默**。

## 5. RAG 上下文渲染在程序端，LLM 只消费

**模式**：检索结果（图谱经验）不直接把原始 JSON 丢给 LLM，而是**程序端渲染成结构化 markdown 块**再注入 prompt。

- `render_reference_experiences_block` 把每条经验拼成固定模板（标题/阶段/因素/执行要点/三段式证据），经验为空时注入一句明确指令"给保守建议 confidence=low"。
- topics_factors 也在程序端展平、过滤后才进 prompt。

**可迁移点**：RAG 里"检索到什么"和"LLM 看到什么"要解耦。程序端渲染能**控制信息密度、去噪、统一格式、注入兜底指令**，比让 LLM 自己啃原始结构更稳、更省 token。空结果的"显式兜底指令"尤其重要——否则 LLM 面对空上下文会自由发挥/幻觉。

## 6. 防御式结构化输出解析

**模式**：LLM 结构化输出永远当"不可信文本"处理，多层兜底解析 + 白名单过滤。

- JSON：`response_format=json_object` → 严格 loads → 去代码围栏 → `raw_decode` 容忍尾部噪声（推理模型爱在 JSON 后带思考）。
- 拼进 Cypher 的 LLM 值先过正则白名单 `_sanitize` 防注入；图谱匹配用 `CONTAINS` 模糊而非等值容忍字面量偏差。
- 枚举值非法就回退默认（stage→S2、confidence→medium）。

**可迁移点**：任何"LLM 输出 → 程序消费"的边界都要有这层防御，尤其当输出会拼进查询语句（注入风险）或驱动控制流（非法值风险）时。**宽进严出**：对 LLM 的格式抖动宽容（多层解析），对进入系统的值严格（白名单/枚举校验/回退）。

## 7. 旁路异步落库：可观测不拖累主链

**模式**：把"记录/落库/上报"这类非核心副作用用 `asyncio.create_task` 旁路化，不 await、失败不影响主响应。

- 策略结果异步写 MySQL（`create_task` 后立即返回），落库失败只记日志。默认开启但可 `--no-storage` 关。
- 配套只读看板 `/results` + 结果表带 `intent_stage` 索引——**在线服务顺手沉淀了可分析的产物**（每次线上决策都留痕，可回溯、可做效果分析）。

**可迁移点**：可观测性/数据沉淀不该阻塞用户请求，也不该因它自己出错而拖垮主链路。旁路异步 + 失败静默（但记日志）是标准姿势。附加价值：在线服务的落库产物本身就是下次迭代的数据集。

## 8. 在线与离线同源编排

**模式**：实时 API、单条脚本、批量回填**共用同一个编排入口**（`build_orchestrator`），只是驱动方式/参数取法不同。

**可迁移点**：批量回填和线上实时如果各写一套逻辑，迟早产物对不齐、行为漂移。让它们调同一段核心代码，差异只在最外层（moment 怎么取、结果往哪写），保证**批量产物与线上产物同源可比**——这对"先批量灰度、再上线"的推进节奏很关键。

## 与写侧方法论的呼应

写侧 [[SalesCopilot 经验蒸馏服务/03-方法论·可迁移模式]] 的核心是"LLM 产信息、程序管一致性/幂等/去重/图谱结构"。本读侧是同一信念在**在线服务**语境下的延续：受控词表（2）、防御式解析（6）、程序端兜底（4/5）都一脉相承，只是把关注点从"写入质量"换成了"在线可用性与成本"。两篇对照着看，能完整看到一套"LLM 深度参与的知识系统"从写到读的工程纪律。
