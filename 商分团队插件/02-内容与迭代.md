## 1. 角色包（Role Pack）

### 1.1 角色清单（示例，最终以后台配置为准）

| 角色 code | 名称 | 服务场景 |
|----|----|----|
| `growth_analyst` | 用户增长商分 | 拉新质量、漏斗、活动归因 |
| `teaching_analyst` | 教研商分 | 完课、教学效果、教师产能 |
| `renewal_analyst` | 续费商分 | 续费率拆解、流失预警 |

### 1.2 角色包结构

服务端动态拼装 `manifest_json` 后返回：

```json
{
  "role": "growth_analyst",
  "version": "2026.05.12-3",
  "checksum": "sha256:...",
  "system_prompt": "你是负责用户增长的商分，遵循以下口径...",
  "skills": [
    {
      "name": "渠道质量分析",
      "path": "skills/channel-quality/SKILL.md",
      "content": "# 渠道质量分析\n\n何时使用：...\n步骤：..."
    }
  ],
  "sql_templates": [
    {
      "id": "tpl_001",
      "name": "渠道 7 日留存",
      "sql": "SELECT ... FROM dwd_user_register WHERE channel = :channel AND dt BETWEEN :start AND :end",
      "params": [
        { "name": "channel", "type": "string", "required": true },
        { "name": "start", "type": "date", "required": true },
        { "name": "end", "type": "date", "required": true }
      ]
    }
  ],
  "metric_defs": [
    { "name": "新用户", "definition": "注册当天且首单完成的用户", "version": "v3" }
  ],
  "tables": [
    {
      "name": "dwd_user_register",
      "columns": [{"name": "user_id"}, {"name": "channel"}, {"name": "dt"}],
      "comments": "用户注册明细表，分区字段 dt"
    }
  ],
  "report_templates": [...],
  "agents": [
    { "name": "data-collector", "content": "..." }
  ]
}
```

### 1.3 客户端装载位置（含 references 三件套）

```
<project>/.claude/skills/<role>/
├── SKILL.md                                ← 每会话覆盖
└── references/                             ← 内容资产的标准目录结构
    ├── tables.md       # 由 tables_meta + table_acl 拼装：可见表、字段中文名、口径、敏感度
    ├── metrics.md      # 由 metric_defs 拼装：口径定义、单位、版本号、可下钻维度
    └── methods.md      # 由 method_defs 拼装：时间窗、显著性、归因方法、异常阈值

<project>/.claude/agents/data-collector.md  ← 每会话覆盖
~/.<插件名>/cache/role_pack.json            ← offline fallback
~/.<插件名>/preferences.md                  ← 永不覆盖（用户私有）
```

**references 三件套的强约束**：所有角色 skill 在强制工作流首条规定——
> 任何取数前先读 `references/metrics.md` 找口径，找不到则**停手**，
> 同时让 data-collector 把"缺口径"产出为候选变更，提示用户上报。

这把"知识在哪里 / 找不到怎么办"从模糊的 prompt 工程变成可执行的硬规则。

### 1.4 离线降级

网关不可达时使用本地 `cache/role_pack.json`，并在 system 上下文中提示"使用本地缓存版本 X（YYYY-MM-DD 同步）"。

## 2. 采集 Agent（data-collector）— 候选变更生成器

> 定位：本轮使用结束后，**把发现的问题/经验提炼为结构化候选变更（带 diff）**，逐条征询用户后上报。
> 反馈池收到的不是模糊文本，而是后台可直接 review 的 diff 草案。

### 2.1 触发与运行模式

- Stop hook 检测到**本轮调用过本插件的 MCP 工具** → 触发 `data-collector` agent
- 后台运行，不打扰用户主线程
- 单次运行限时（建议 30s 内），超时直接放弃本轮采集

### 2.2 Agent 定义文件（由网关下发，每角色可定制）

文件位置：`.claude/agents/data-collector.md`

核心 prompt 骨架：
```markdown
---
description: 把本轮使用中发现的问题/经验提炼为结构化候选变更，逐条征询用户后上报
---

你是「候选变更生成器」，每轮对话结束后被触发。

输入：
- 本轮 transcript（提问、思考、工具调用、最终回答）
- 本轮 MCP 调用日志（SQL/template/失败原因/结果行数）

任务：
1. 识别本轮存在的缺口或经验：
   - 缺指标口径（metrics.md 命中失败）
   - 缺 SQL 模板（多轮试错才命中）
   - 缺方法（无显著性 / 阈值 / 时间窗规则）
   - 表元数据有误（字段中文名、口径、分区说明不准）
   - 报告样式反馈
   - 错误经验（同样错误已发生第 2 次）
   - **稳定的个人使用模式**（连续 N 次同样的口径/维度选择）→ 追加 preferences
2. 把每条提炼为 **candidate_change**（结构见下）：
   - 分类、目标文件、变更摘要、diff（或新增片段）、风险
3. 本地脱敏（手机号/邮箱/订单号/金额）
4. 用 AskUserQuestion 让用户**逐条勾选**确认
5. 用户确认后：
   - 类别非 `preference`：调 `submit_feedback({ batch_id, candidates: [...已确认] })`
   - 类别为 `preference`：append-only 写 `~/.<插件名>/preferences.md`（不删除既有内容）

红线：
- 默认全部不勾选
- 单次最多 5 条候选，超出则建议拆批
- 任何敏感字段（手机号、订单号、金额）必须先脱敏再写进 candidate.diff
```

### 2.3 候选变更（candidate_change）数据结构

```yaml
batch_id: 2026-05-12T14:33:00+08:00
source_session: <transcript_hash>            # 不含明文 transcript
target_role_pack: growth_analyst
candidate_changes:
  - id: C1
    category: sql_template                   # metric | sql_template | method | table_doc | skill | preference
    target_file: skills/channel-quality/sql-templates/retention-by-region.sql
    summary: "新增按地域分组的 7 日留存模板"
    change_type: add                         # add | modify | remove
    diff_or_new: |
      + WITH base AS (
      +   SELECT user_id, region, DATE(register_time) AS d
      +   FROM dwd_user_register WHERE dt BETWEEN :start AND :end
      + )
      + SELECT ...
    risk: "region 非分区字段，大表扫描需评估性能"
    user_confirmed: false                    # AskUserQuestion 勾选后由本地置 true

  - id: C2
    category: metric
    target_file: references/metrics.md
    summary: "修正「新用户」口径：增加未退款约束"
    change_type: modify
    diff_or_new: |
      - 注册当天且首单完成的用户
      + 注册当天且首单完成且未退款的用户
    risk: "影响历史报告口径一致性，需固化为 v4 并保留 v3"
    user_confirmed: false

  - id: C3
    category: preference                     # → 不上报，append 到本地 preferences.md
    target_file: ~/.<插件名>/preferences.md
    summary: "你最近 3 次都按 source_id 而非 channel_name 看渠道"
    change_type: add
    diff_or_new: |
      ## 常用维度（新增）
      - 渠道分析默认按 source_id
    risk: "无"
    user_confirmed: false
```

### 2.4 用户交互范式

```
data-collector：本轮我整理了 3 条候选变更，请逐条勾选要上报/采纳的：

[C1] 新增 SQL 模板「按地域 7 日留存」
     → 上报到团队反馈池（运营 review diff 后并入下版角色包）
     风险：region 非分区字段

[C2] 修正「新用户」口径（增加未退款约束）
     → 上报到团队反馈池
     diff：
       - 注册当天且首单完成的用户
       + 注册当天且首单完成且未退款的用户

[C3] 写入你本地的个人偏好（不上报）
     → ~/.<插件名>/preferences.md
     "渠道分析默认按 source_id"

（默认全不勾选；勾选后才行动）
```

**关键原则**：
- 默认**不自动勾选任何项**
- 脱敏**在本地完成**，再发送
- 个人偏好只 append 到本地，**不上报**给后台
- 单次超 5 条建议拆批

### 2.5 脱敏规则（可配置）

最小默认规则：
- 手机号：`1\d{10}` → `***`
- 邮箱：`\S+@\S+` → `***@***`
- 订单号：`(ORD|TXN)\d{6,}` → `***`
- 金额（>=1000）：保留量级，截断个位

规则文件由网关下发，与角色包一起更新。

## 3. 管理后台

### 3.1 技术栈

- 后端：FastAPI（可与 MCP 网关同进程或独立）
- 前端：极简（一个内部 SPA 即可，Next.js 或 plain HTML）
- 登录：内部口令 / 复用现有内部平台 SSO（运营人数很少，方案极简）

### 3.2 模块

| 模块 | 关键功能 |
|------|---------|
| **Token 管理** | 一用户一 token：按 `user_label` 检索，存在则在该 token 上**追加角色包绑定**（token 字符串不变），不存在则新建 token 并绑定本次审批角色包（**token 字符串仅展示一次**）。支持单角色解绑、token 一键吊销、续期、查看用量 |
| **表元数据探索** | 用只读账号扫描业务 MySQL → 写入 `tables_meta` 初稿（字段名、类型）→ 运营在后台补字段中文名、口径、敏感度 → 发布 |
| **内容仓库** | skill / SQL 模板 / 口径 / 报告模板 的版本化编辑；diff 视图；双人审核 |
| **角色包编排** | 选择 skill/模板/口径 + 配置 `table_acl` → 拼出 role_pack_versions → 发布或灰度 |
| **反馈池** | 接收 data-collector 上报的**结构化候选变更包**（带 diff、风险、目标文件）；按 category 分流到对应内容编辑流；运营 review diff 即审核，一键采纳 → 自动生成内容仓库 PR 草案 |
| **灰度发布** | 按 token 白名单 / 角色 / 比例灰度新版能力包；一键回滚 |
| **审计中心** | SQL 调用日志检索（按 token / 角色 / 表 / 时间窗）；版本发布日志 |
| **监控看板** | 工具调用量、成功率、人均时长、反馈采纳率（M2 阶段） |

### 3.3 表元数据探索流程

```
1. 后台 → 触发"业务库扫描"
2. 网关用只读账号执行 SHOW TABLES / DESCRIBE
3. 写 tables_meta：name/columns_json/last_synced_at
4. 运营进表元数据页面：
   - 补字段中文名
   - 补口径说明（关联到 metric_defs）
   - 标 sensitivity
   - 指定 owner
5. 标记为"已发布"，可被角色包引用
```

## 4. 关键流程

### Flow A — 用户首次使用

```
用户在 OA 提单（选角色 + 写理由）
       ↓
OA 审批通过
       ↓
运营在后台按 user_label 检索：
  - 已有 token？→ 追加绑定本次角色包（token 字符串不变）
  - 无 token？  → 新建 token 并绑定，token 字符串仅展示一次
       ↓
token / 角色生效通知通过 OA 工单或 IM 发回给用户
       ↓
首次：用户 /<插件名> token set <token>
       ↓
/<插件名> role list  → 看到自己被授予的角色包
/<插件名> role use <code> → 选定本会话使用的角色
       ↓
（可选）/<插件名> prefs edit 填本地偏好
       ↓
启动 Claude Code → SessionStart 按 active_role 拉角色包 + 注入 preferences
       ↓
提问 → Claude 用 skill + 模板 → 调 MCP → 网关执行 → 返回
       ↓
Stop hook → data-collector 提炼候选变更 → 用户逐条勾选 → 上报反馈池 / 写入本地偏好
```

### Flow A' — 老用户新增角色

```
用户在 OA 二次提单（申请新增角色）
       ↓
OA 审批通过
       ↓
运营后台：在该用户已有 token 上追加角色包绑定
       ↓
（无需重新发 token，用户无感）
       ↓
用户下次 /<插件名> role list 即可看到新角色
       ↓
/<插件名> role use <新角色 code> → 切换
```

### Flow B — 商分专家迭代口径

```
后台编辑「新用户」口径 v3 → v4（注册口径放宽）
       ↓
双人审核（编辑人 + 审核人）
       ↓
发布 → 新建 role_pack_versions（包含 v4）
       ↓
灰度 20% token（gray_rule_json）
       ↓
看 audit_log 中 v4 的调用量 + 反馈池
       ↓
全量发布 → current_version 切换
       ↓
所有持有该角色 token 的用户下次启动自动拉新版
（preferences.md 不受影响）
```

### Flow C — 采集飞轮闭环（候选变更驱动）

```
用户 A：问"按地域看 7 日留存"
       ↓
Agent 走流程：读 references/metrics.md 命中"留存"
              读 references/tables.md 未命中"地域"分组模板
              试错 → 多轮才拼出可用 SQL
       ↓
Stop hook → data-collector 提炼出 2 条候选：
  C1: category=sql_template，新增 retention-by-region.sql（带完整 SQL diff）
  C2: category=table_doc，dwd_user_register 补 region 字段描述
       ↓
用户勾选 C1+C2 → submit_feedback 上报
       ↓
反馈池按 category 分流：
  C1 → SQL 模板编辑流（运营 review diff → 性能评估 → 采纳）
  C2 → tables_meta 编辑流（核对业务库 → 采纳）
       ↓
两条 PR 草案自动生成 → 双人审核 → 发布 → 灰度 → 全量
       ↓
用户 A 下次启动自动获得新能力
（可选：系统在欢迎信息中提示"你之前的反馈已上线"）
```

### Flow D — 灰度异常回滚

```
新版本上线后 audit_log 中错误率上升 / 反馈池负面集中
       ↓
后台一键回滚 → role_pack_versions.status 改 rolled_back
       ↓
current_version 切回上一稳定版本
       ↓
所有用户下次启动拉回旧版
       ↓
问题修复后再次走灰度
```

## 5. 内容生命周期与版本治理

- **所有内容资产**（skill、sql_template、metric_def）独立版本号
- 角色包版本号格式：`YYYY.MM.DD-N`（N 为当日发布序号）
- 历史报告引用：报告模板生成时固化所用 metric 的版本号 → 数月后查询旧报告仍能复现口径
- 回收策略：连续 N 个版本未被引用的 asset 标 `archived`，不再下发但保留历史

## 6. 反馈池的"转化"规范

反馈不是越多越好，关键是**收敛到内容更新**。运营 SLA 建议（按候选变更的 category 分类）：

| category | 含义 | 处理目标 |
|----------|------|---------|
| `metric` | 指标口径修正或新增 | 一周内 triage，双人审核后合入下个 metric_defs 版本 |
| `sql_template` | SQL 模板新增或修正 | 一周内 triage，性能评估通过后并入角色包 |
| `method` | 分析方法/阈值/时间窗 | 月度评估是否合并到 method_defs |
| `table_doc` | 表元数据（中文名/口径/分区）修正 | 三天内核对业务库后合入 tables_meta |
| `skill` | skill 内容补充（澄清/红线/工作流） | 月度评估 |
| 任意类别带 `change_type: bug` 风险描述 | Bug 类 | 24h 内 triage，48h 内修复或回滚 |

> 注：`category: preference` 不进入反馈池，只 append 到用户本地 preferences.md。

每月发布"反馈采纳报告"：本月候选 N 条 → 采纳 M 条 → 上线 K 条 → 影响 X 个用户。
