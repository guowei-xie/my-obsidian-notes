# 后端架构与执行器范式

> 子笔记 · 回 [[00-总览]]。本篇讲清「后台那些长时作业怎么跑、崩了怎么自己爬起来」——本项目工程上最值得学的部分。

## 技术架构

```
React SPA (Vite + Antd 6 + react-router 7)
   │ REST (JWT)
FastAPI (uvicorn，单 worker，systemd/supervisor 托管，不用 Docker)
   ├── 业务 API：labels / tuning_tasks / judge_tasks / annotation_tasks
   │              / validation_sets / compare_tasks / prompts / providers
   │              / samples / timeline / audit_logs   （backend/app/api/*.py）
   ├── 飞书 OAuth 模块（services/feishu.py）
   ├── 判定执行器 judge_executor（asyncio 并发 worker，进度写库，断点续跑）
   ├── AI 裁决器 adjudication（确定性规则 + 调优模型推断，明细驱动、可重入）
   ├── 迭代调优引擎 tuning_executor（轮次状态机驱动，重启自动恢复）
   └── 导出生成器 export（异步 zip，落盘 + 下载令牌）
线上 MySQL (bitest 库，slt_ 前缀) + 应用服务器本地磁盘（样本原件、导出包）
```

- 依赖（`pyproject.toml`）：`fastapi / sqlalchemy 2.0 / alembic / pymysql / cryptography / pydantic 2 / httpx / openai / PyJWT`；Python ≥ 3.12，uv 管理，ruff lint（选 `E/F/I/B/UP/BLE`）。
- 前端（`package.json`）：React 19、Antd 6、axios、react-markdown、react-router 7；oxlint + vitest。
- **后台执行采用「库表驱动的任务队列 + FastAPI 内嵌 asyncio worker」**，单机即可跑数千~数万条判定；PRD 称量级上来可平滑替换 Celery/RQ 而不改表结构。

## 执行器范式（本项目的工程内核）

四个后台组件——判定执行器、AI 裁决器、迭代引擎、标注报告——共享**同一套设计范式**。这套范式是整个仓库最可迁移的资产。

### 1. 库表状态即断点，续跑幂等

作业的进度**不放内存、放库表状态字段**，每个可恢复单元都是一行带 status 的明细：
- 判定：`slt_judge_results` 逐条明细——重启后「按未完成明细自动续跑」，已完成样本不重复计费（幂等）。
- 迭代：`slt_tuning_rounds` 的 `status(rewriting → judging → comparing → done/failed)`——「轮次表即断点」，某轮跑到一半崩了，重启从该轮当前 status 续。
- 裁决：验证集条目 `status=pending` 即待办；`building` 状态的验证集重启续跑。

*效果*：进程随时可被杀/重启/滚动更新，作业不丢、不重、不需要外部队列中间件。

### 2. 进程内注册表做实时控制

暂停/取消/正在跑，用**进程内的模块级变量**表达，而非库轮询：
```python
# services/tuning_executor.py
_running: set[int] = set()          # 正在迭代的调优任务
_control: dict[int, str] = {}       # tuning_task_id → "pause" | "cancel"
```
API 收到暂停/取消时往 `_control` 写指令，正在跑的 worker 在检查点读取并响应；迭代引擎的暂停/取消会**同时向引擎与当前判定运行下发**（引擎串行 await 单轮判定运行，两处控制要同步）。

### 3. 单 worker 强约束 + 文件锁护栏

注册表是进程内状态 → **多 worker/多实例会重复跑任务且控制指令失灵**。项目用文件锁在启动时兜底（`main.py:34-64`）：
```python
def _acquire_executor_lock():
    # 抢 storage_dir/.executor.lock 的排他非阻塞锁
    # 抢不到 → 已有实例在跑 → 本进程只服务 API、不拉起 resume_*
```
`lifespan` 里抢到锁才依次拉起四个恢复钩子：
```python
await resume_running_tuning_tasks()                        # 先恢复迭代（含其验证判定运行）
await resume_running_tasks(skip_task_ids=engine_driven_run_ids())  # 判定恢复跳过引擎接管的运行，防双方争抢
await resume_building_validation_sets()                     # 恢复中断的裁决
await resume_pending_reports()                              # 补建未物化的标注报告
```
> 抢不到锁的进程会 `logger.error` 明确提示「uvicorn 必须单 worker 部署」，只服务 API。部署文档也强调**必须单 worker**（README/PRD 一致）。恢复顺序有讲究：先恢复迭代引擎、再恢复判定并显式跳过被引擎接管的判定运行，避免两个恢复器抢同一个 judge run。

### 4. 复用 + 分层，不重复造

- **迭代引擎复用判定执行器**：阶段 3 每轮的验证判定不另写一套，直接调 `judge_executor`——断点续跑/并发/遵从率观测「白拿」；引擎只负责串行编排「改写 → 判定 → 比对」。
- **改写参数与判定参数分离**：`effective_tuning_params` 专门给改写阶段兜底大 `max_tokens`/`timeout`——因为改写输出整段新 Prompt，远长于逐条判定输出、也远慢；复用判定的小值会截断致 JSON 非法或超时。这个函数被「实际调用」与「固化进报告」两处共用，避免逻辑漂移。
- **LLM JSON 解析自适应**：改写产物被截断时逐次翻倍 `max_tokens`（上限 32768），仍不行则以「被截断」的可读错误落库交人工处置（调大端点上限或精简 Prompt）。

## 其它工程约束

- **API 全程 no-store**：中间件对所有 `/api/` 响应加 `Cache-Control: no-store`，防浏览器/反代把轮询 GET 按 URL 缓存返回旧体（前端 `api/client.ts` 另加时间戳防缓存）。
- **统一异常兜底**：未捕获异常统一 500 + 完整堆栈进日志、用户只看可读文案。
- **密钥加密**：模型 `api_key` 后端加密存储（`core/crypto.py`）、前端不回显、不出后端。
- **配置单一源**：`backend/config.ini`（`SLT_` 前缀环境变量可覆盖单项）；端口/前端地址集中在 `[server]` 段，`cors_origins` 与飞书 `redirect_uri` 留空时自动派生。
- **部署**：`scripts/deploy.sh` 一键滚动更新（拉码 → 后端 `uv sync` + `alembic upgrade head` → 前端 `npm ci && build` → 重启 systemd → `/api/health` 健康检查），失败自动回滚代码/依赖/前端产物（DB 迁移不自动回退）。
