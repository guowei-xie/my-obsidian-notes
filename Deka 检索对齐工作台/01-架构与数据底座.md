# 架构与数据底座

> 展开总览的「核心功能逻辑」段：数据底座怎么摆、四个锁死轴是什么、组件如何连线、session 状态机怎么走。

## 组件连线

一句话：**Web UI ↔ FastAPI 后端**，后端对接四个外部服务。（README §Setup 的 mermaid 图）

```
Web UI (React+Vite) ──HTTP + cookie session──▶ Deka 后端 (FastAPI · deka-web)
   后端 ──embed query/spans──▶ Embeddings 服务 (dense + learned-sparse)
   后端 ──vector search · RRF fusion──▶ Milvus (chunk 向量)
   后端 ──reflect · derive rubric · judge──▶ OpenAI 兼容 LLM
   后端 ┈┈原文查找（可选）┈┈▶ PostgreSQL (源转写)
   Embeddings ┈┈writes vectors┈┈▶ Milvus
```

- **鉴权**：web UI 每个请求都过一层签名 cookie session，keyed 到 `users.yaml`。token 只存 **SHA-256**，明文 token 仅用于登录。可选 `DEKA_SESSION_SECRET` 让 session 跨后端重启存活。（README §3；`src/auth/`）
- **单机替代**：`npm run build` 后由后端直接在 `127.0.0.1:8787` 托管前端。
- **Provider 无关**：embedder 只要是「返回 dense+sparse 的 HTTP 服务」，LLM 只要 OpenAI 兼容端点即可——harness 不绑任何模型厂商。（whitepaper §Code availability）

## 数据底座（the substrate）

Milvus collection 里**每行 = 一条对话转写的一个 chunk**，每个 chunk 挂两个 BGE-M3 学到的表示：

| 向量字段 | 维度/度量 | 管什么 |
|---|---|---|
| `dense_embedding` | 1024 维，COSINE | 语义相似（概念性问题走这路） |
| `sparse_embedding` | learned-sparse，IP（inner product） | 词汇关联——桥接口语↔正式词（客户口语「太贵了」能对上「价格敏感」这种正式表述） |

**为什么必须两路 + 每查询单独调**（whitepaper §1）：概念性问题（「销售如何建立信任」）dense 路最好；口语抱怨（informal register 的「太贵了」）sparse 路最好。没有一个固定配比对所有查询类型都好，所以每个查询都要单独 tune。

**RRF 融合**（whitepaper §3.1）：一个查询同时打两路，两个排名列表用 reciprocal-rank fusion 合并——候选融合分 = Σ over active paths of `1/(rrf_k + r)`，`r` 是它在该路里的排名。**用排名位置而非原始分数**，因为 dense 的 cosine 分（0–1）和 sparse 的 IP 分（0.1–0.5）尺度不可比，rank fusion 让组合 scale-free。→ 推论：**给两路加权不是可调轴**，唯二的杠杆是「每路贡献多少候选」和「rank 衰减曲线多平」。

**退役的第三路 BM25**（whitepaper §3.1，值得学的取舍）：schema 曾带一个 BM25 全文索引，但被移出 Phase 1——默认 tokenizer 不切中文，短关键词查询还能打分，但这个工作台针对的长短语查询会碎成一堆无匹配 token 返回空。它几乎不贡献 FIT，却给反思 agent 多塞了一个会误导的旋钮，于是被砍。**字段仍留在 schema 上**，未来上中文感知 tokenizer 可无迁移地恢复。

**PostgreSQL 伴库**：存 chunk 分片前的**原始整段文本**，同主键。检索本身全在 Milvus 跑；Postgres 只在人/LLM judge 要读上下文时才查。（whitepaper §3.1；`src/postgres/`，`config.yaml` 的 `postgres` 段）

**scope 注册表**：collection 与 table 都不硬编码——`scopes.yaml` 把人可读名字映射到 `{milvus_collection, postgres_table}`，一套部署可服务多个语料，操作者开 session 时选 scope。（whitepaper §3.1；`src/scopes/`）

## 四个锁死轴（the four locked axes）

Phase 1 只暴露四个搜索参数，**第一轮开始的瞬间全部冻结**（whitepaper §3.2）。它们是「高效抵达目标的脚手架，不是目标本身」：

| 参数 | 角色 | 默认值 |
|---|---|---|
| `rrf_k` | rank 融合平滑常数；越大越拉平 rank 衰减曲线 | 60 |
| `per_path_limit` | 融合前每路贡献多少候选 | 20 |
| `top_k` | 每轮操作者看到多少融合 chunk——**是每轮阅读预算，不是语料覆盖上限** | 10 |
| `active_paths` | 哪几路喂融合：dense / sparse / 两者 | [dense, sparse] |

- `top_k` 的关键区分：它只 bound 人每轮的阅读负荷；「覆盖全库」这个交付承诺由后面的 Harvest 兑现，不靠放大单轮展示。
- 另有 `min_survivors`（默认 5，≤ top_k）：post-filter 后若存活行不足，`run_search` 自动翻倍 `per_path_limit`（最多 3 次），保证操作者总有足够候选可评。（`config.yaml.example` search 段）
- **为什么锁死**（whitepaper §2）：中途改旋钮会 confound 操作者正在读的信号。反思**不提议新参数值**，只产出 observe→diagnose→hypothesise 的推理轨迹。唯一允许的中途变更是一次门控严格的 path drop（见 [[02-四阶段方法]] 的 audit 段）。

## Session 状态机

session 走一个显式状态机（`src/session/state.py` 的 `_VALID_PHASES`）。只有 Phase 1 循环；Phase 2–4 是单次前向，各带自己的 review gate；被拒绝或被配置关闭的阶段直接路由到 `DONE`。

```
TUNING（Phase 1 循环）
  └─收敛─▶ ANCHOR_CONFIRM ─▶ ANCHOR_RUNNING ─▶ ANCHOR_DONE   (Phase 2)
       └─▶ REFINE_CONFIRM ─▶ REFINE_DERIVING ─▶ REFINE_EDITING
              ─▶ REFINE_JUDGING ─▶ REFINE_REVIEW              (Phase 3)
                 （discard 则回 REFINE_EDITING，rubric 版本 +1）
       └─▶ APPLY_CONFIRM ─▶ APPLY_TRAINING ─▶ APPLY_PREPARING
              ─▶ APPLY_REVIEW（拖 slider 可重入）─▶ APPLY_APPLYING  (Phase 4)
  ─▶ DONE
（失败态：ANCHOR_FAILED / REFINE_FAILED / APPLY_FAILED）
```

- **外化状态是可续跑的关键**：每轮 append 到磁盘 progress log；从磁盘恢复的 session 直接在正确的行重进工作流，不重跑之前阶段。（whitepaper 附录）
- **严格前向**：没有任何箭头从后面的阶段回到前面的——返工靠**重跑一个阶段**，不靠回接已完成的阶段。
- `SessionState` 里跨屏状态（`refine_state` / `apply_state`）用 `Any` 存，刻意让 `state.py` 不 import refine/apply，保持核心状态层零依赖。

## 收敛判定（三重门的代码落点）

`SessionState.is_converged`（`src/session/state.py`）：

```
latest_precision >= convergence.precision_at_k   # 默认 0.8
  AND len(cumulative_fit_pks)     >= min_fit      # 默认 15
  AND len(cumulative_not_fit_pks) >= min_not_fit  # 默认 3
```

- 三个阈值在 session 创建时从 `harvest.{min_fit,min_not_fit,precision_at_k}` + 覆盖项**快照冻结**（`ConvergenceThresholds`），这样中途改 YAML 不会把门挪到正在跑的操作者脚下。
- 精度计算只算 FIT+NOT_FIT，**DISCARD 不进分母**——DISCARD 是逃生舱（issue #46），不是裁决，不稀释精度信号。（`complete_turn`）
- 累计 FIT/NOT_FIT 按 PK 去重，跨轮 union；每轮结束把看过的 PK（含 per-path top-3 候选）并入 `seen_pks`，后续搜索用 Milvus `expr` 排除，保证每轮出新料。
