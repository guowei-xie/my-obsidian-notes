### 关键架构决策

| 决策 | 选择 | 理由 |
|------|------|------|
| Agent 编排模式 | 顺序流水线（标签→策略） | 策略生成依赖标签结果，不可并行 |
| LLM 选型策略 | 分级：高频分类用 Qwen/DeepSeek，复杂推理用 Claude | 成本与质量平衡 |
| 向量检索 | Milvus | 已有基建，对话 & 经验检索复用 |
| 缓存策略 | 标签 TTL=24h，策略=按需生成 | 标签相对稳定，策略需要时效性 |

## Agent 设计

### Agent 1: 标签体系构建 Agent

**定位：** 设计时工具，非运行时。供策略团队使用，用于扩展和维护标签体系。

```yaml
类型: 设计时 Agent（离线、人工触发）
输入:
  - 新业务场景描述
  - 可用数据源清单
  - 现有标签体系
输出:
  - 新增标签建议（含计算逻辑）
  - 标签间关联关系
  - 评估所需数据是否就绪

Prompt 策略: Few-shot，以现有标签定义为示例
使用频率: 低（标签体系调整时）
```

**示例交互：**
```
输入: "续报场景下，需要识别用户的'续费阻力来源'，现有数据有对话记录和履约数据"

输出:
  建议新增推断标签:
    1. "续费阻力类型" — 枚举: [效果不达预期, 兴趣衰减, 服务不满, 竞品替代, 经济压力]
       计算逻辑: 从续报期对话中抽取，需匹配关键表达模式
       依赖数据: 对话记录 ✓ 已就绪

    2. "学习成果满意度" — 枚举: [满意, 一般, 不满意]
       计算逻辑: 综合对话表达 + 履约数据(完课率>80% & 作品提交>5)
       依赖数据: 对话记录 ✓ + 履约数据 ✓ 均已就绪
```

### Agent 2: 标签提取 Agent

**定位：** 运行时核心 Agent，从对话数据中提取 L3 推断标签。

```yaml
类型: 运行时 Agent（批量 + 按需触发）
输入:
  - 对话文本（结构化格式）
  - 用户画像上下文（L1/L2 标签）
  - 标签体系定义（当前版本）
输出（三层结构：话题 → 因素 → 意向）:
  - 话题×因素: [{topic, factors: [{polarity, tag, proof, time}]}]
  - 积极因素汇总: [{tag, proof, time}, ...]
  - 消极因素汇总: [{tag, proof, time}, ...]
  - 意向分类: S0-S4 + 置信度 + 推导理由

处理流程:
  Step 1: 识别对话中涉及的话题
  Step 2: 在每个话题下提取积极/消极因素（附原文证据）
  Step 3: 综合所有话题×因素，推导意向阶段

Prompt 策略:
  - 结构化输出（JSON Schema 约束）
  - CoT 推理（先识别话题→再提取因素→最后推导意向）
  - 标签定义 & 示例内嵌于 System Prompt

模型选择: Qwen-Plus / DeepSeek-V3（高频调用，需控制成本）
延迟要求: P95 < 10s（批量），P95 < 5s（按需）
评估方式: 复用 rqi_prompt_eval 框架，F1 ≥ 0.80
```

**Prompt 结构草案：**
```
System:
  你是一个销售对话分析专家。请按以下步骤分析对话：
  1. 先识别对话中涉及了哪些话题
  2. 在每个话题下，提取用户表达中的积极因素和消极因素，附上原文证据
  3. 综合所有话题和因素，推导用户的购买意向阶段

  ## 话题清单
  学习情况、学习目标、课程了解、课程体验、价格费用、
  时间安排、决策过程、竞品比较、孩子兴趣、比赛/考级

  ## 因素标签体系
  积极因素: [学习兴趣, 目标明确, 主动询价, 主动约课, 社交背书,
             体验认可, 竞赛需求, 时间窗口明确, ...]
  消极因素: [价格敏感, 决策权模糊, 时间冲突, 效果怀疑,
             兴趣不足, 竞品倾向, 年龄顾虑, ...]

  ## 意向分类定义（由话题×因素推导）
  S0: 暂缓/流失 — 明确拒绝信号，或消极因素压倒性主导
  S1: 沉默用户 — 无话题交集，或话题极少且无因素信号
  S2: 需求模糊 — 有话题交集，有弱积极因素，但未形成明确方向
  S3: 需求明确 — 多话题下积极因素主导，主动表达需求
  S4: 强购买意愿 — 出现强购买信号（询价/约课/问报名）

  ## 输出格式
  {
    "topics_factors": [
      {
        "topic": "话题名",
        "factors": [
          {"polarity": "positive|negative", "tag": "因素标签", "proof": "原文引用", "time": "时间"}
        ]
      }
    ],
    "positive_factors": [{"tag": "...", "proof": "...", "time": "..."}],
    "negative_factors": [{"tag": "...", "proof": "...", "time": "..."}],
    "intention": "S0|S1|S2|S3|S4",
    "intention_reason": "基于以上话题和因素的综合推导理由",
    "confidence": 0.0-1.0
  }

User:
  ## 用户背景
  年级: {grade}, 城市: {city}, 渠道: {channel}
  体验课完课率: {completion_rate}, Leads评分: {leads_score}

  ## 对话记录
  {dialogue_text}
```

**批量 vs 按需触发：**
- **批量模式：** 每日凌晨对前一天新增对话批量处理，更新全量用户标签
- **按需模式：** 销售请求策略卡片时，若用户标签已过期，触发实时提取

### Agent 3: 销售经验蒸馏 Agent

**定位：** 离线批量 Agent，从 Top 销售的成功对话中提取可复用的销售模式。

```yaml
类型: 离线 Agent（定期批量执行）
输入:
  - 高转化对话样本集（按结果筛选：成交用户的完整对话历史）
  - 对话关联的用户画像和标签
  - 对比组：低转化对话样本集（相似用户条件，未成交）
输出:
  - 阶段性策略模式（每个 S 阶段的有效做法）
  - 异议-应对模式库（常见异议 + Top 的化解方式）
  - 关键转折点模式（什么行为促成了意向跃迁）

Prompt 策略:
  - 长上下文分析（多轮对话的全量输入）
  - 对比分析框架（成功 vs 失败的对照）
  - CoT 深度推理

模型选择: Claude Sonnet / Opus（低频调用，需要深度推理）
执行频率: 每周/每月（随新成交数据积累）
```

**蒸馏流程：**
```
Step 1: 样本筛选
  - 成功组: 成交用户，筛选对话质量高的样本
  - 对照组: PSM 匹配的未成交用户样本
  ↓
Step 2: 模式识别
  - 按意向阶段分组
  - 识别成功组共性行为 & 对照组缺失行为
  ↓
Step 3: 模式结构化
  - 场景: 用户在 S2 阶段 + 阻塞因素为"价格敏感"
  - Top 做法: 先强化价值认知，再给出"投入产出比"框架，最后提供灵活方案
  - 关键要素: 不急于让价，而是改变"贵"的参照系
  ↓
Step 4: 向量化存储
  - 蒸馏出的模式存入 Milvus
  - 检索键: (intent_stage, factor_combination)
  → 供 Agent 4 实时检索
```

**副产品：销售教练（模拟对练）**
```
蒸馏出的经验模式 → 可驱动一个"模拟用户"Agent
  - 模拟特定画像的家长
  - 按剧本抛出异议
  - 评价销售的应对质量
  → 训练新人、薄弱环节专项练习
```

### Agent 4: 策略生成 Agent

**定位：** 运行时核心 Agent，为销售实时生成个性化回访策略。

```yaml
类型: 运行时 Agent（按需触发）
输入:
  - 用户当前标签（L1 + L2 + L3）
  - 用户历史交互摘要
  - 相似场景的经验模式（从 Milvus 检索）
  - 当前场景上下文（首课前 / 续报前）
输出:
  - 策略卡片（结构化 YAML/JSON）

Prompt 策略: RAG（检索增强生成）
  - 检索: 根据用户标签组合，从 Milvus 检索 Top-K 相关经验模式
  - 生成: 结合用户具体情况 + 经验模式，生成个性化策略

模型选择: Qwen-Plus / DeepSeek-V3（高频调用）
延迟要求: P95 < 5s（销售等待生成）
降级策略: 超时则返回基于标签组合的模板策略
```

**RAG 流程：**
```
1. 构建检索 Query
   - intent_stage + top_factors → 向量化
   ↓
2. Milvus 检索
   - 找到 Top-5 最相关的经验模式
   ↓
3. Context 组装
   - System Prompt: 策略生成规则 + 输出格式
   - 经验模式: 作为参考案例注入
   - 用户信息: 当前标签 + 历史摘要
   ↓
4. LLM 生成
   - 输出结构化策略卡片
   ↓
5. 后处理
   - 格式校验
   - 写入策略推荐表
   - 推送至销售端
```

### Agent 5: 质量评分 Agent

**定位：** 批量 Agent，对已完成的对话进行服务质量评分。

```yaml
类型: 运行时 Agent（批量，每日执行）
输入:
  - 对话文本
  - 用户标签（当前阶段）
  - 关键事件清单（当前阶段应发生的事件列表 + 权重）
输出:
  - 关键事件识别结果（是否发生 + 质量评分 + 证据）
  - 信号响应识别结果（信号 + 是否响应 + 是否缓解）
  - 综合质量评分

模型选择: Qwen-Plus（批量处理，成本敏感）
评估方式: 人工标注对照，Cohen's Kappa ≥ 0.70
```

## 反馈闭环设计

> **真正难的不是模型能力，而是业务反馈闭环。能闭环才能进化。**

一个功能单元 = 规则 + 机器学习 + LLM，根据场景进行编排。
但如果没有闭环，系统只能靠初始设计吃老本，无法自我进化——这才是大部分 AI 项目"不温不火"的根源。

### 为什么需要闭环

```
没有闭环:
  蒸馏经验 → 生成策略 → 销售使用 → ???
  （不知道策略好不好，模型不会进步，最终沦为"摆件"）

有闭环:
  蒸馏经验 → 生成策略 → 销售使用 → 追踪结果 → 评估效果 → 优化模型
  （策略质量持续提升，系统越用越准）
```

**闭环的关键挑战：**
- 奖励信号滞后：成交周期长（数周到数月），策略→结果的因果链很长
- 归因困难：用户转化是多因素共同作用，难以归因到单一策略
- 冷启动：初期没有足够的 (策略, 结果) 对来评估效果

**应对策略：**
- 不等最终转化，先用"意向阶段变化"作为近端奖励信号（中间指标）
- Phase 2 即开始采集反馈数据，不等 Phase 4 才建闭环
- 初期以"A/B 对比 + 人工评审"替代自动化评估

### 三层反馈机制

#### Level 1: 显式反馈（短期）

```
触发: 销售使用策略后
采集:
  - 是否查看了策略卡片 → was_viewed
  - 是否采纳了策略建议 → was_applied
  - 主观评价（有用/没用/部分有用）→ counselor_feedback
价值: 快速迭代策略呈现方式、过滤低质量策略
```

#### Level 2: 隐式反馈（中期）

```
触发: 用户阶段发生变化 / 成交 / 流失
采集:
  - 策略生成后，用户意向是否按预期方向流转
  - 使用了策略的用户 vs 未使用策略的用户，转化差异
  - 同一策略在不同销售手中的效果差异
价值: 评估策略的实际业务效果
```

#### Level 3: 模型迭代（长期）

```
触发: 积累足够 (策略, 上下文, 结果) 三元组后
动作:
  1. 经验库更新: 将新的成功案例纳入蒸馏，淘汰效果差的旧模式
  2. 检索权重调整: 效果好的经验模式提升检索权重
  3. Prompt 优化: 基于效果数据调优 Agent Prompt
  4. 评估基准更新: 用最新标注数据更新评估集

注意: 初期不建议做端到端的强化学习（RLHF），
      原因是样本量不足 + 奖励信号滞后（成交周期长）。
      先用"数据驱动的迭代优化"即可。
```

### 闭环数据流

```
策略推荐表                      推断标签表（前后对比）
  ├─ strategy_id               ├─ 策略前 intent_stage
  ├─ was_viewed                ├─ 策略后 intent_stage（Δ）
  ├─ was_applied               └─ 结果标签 (converted/not)
  └─ counselor_feedback
           │                           │
           └───────────┬───────────────┘
                       ↓
              策略效果评估样本
              (strategy_id, context, action, outcome)
                       │
           ┌───────────┴───────────┐
           ↓                       ↓
    经验库更新                Prompt/检索优化
    (Milvus 向量权重)        (A/B test 验证)
```

## 集成架构

### 与现有系统的集成

| 系统 | 集成方式 | 数据流向 |
|------|---------|---------|
| CRM | API 嵌入策略卡片 | Sales Copilot → CRM（推送策略） |
| 企业微信 / IM | 侧边栏或消息卡片 | Sales Copilot → IM（展示策略） |
| 对话系统 | API 拉取对话记录 | 对话系统 → Sales Copilot |
| 数据仓库（Hive） | 批量 ETL | Hive → Sales Copilot（用户特征） |
| 埋点平台（Sensors） | 批量 ETL | Sensors → Sales Copilot（行为数据） |

### 部署架构

```
┌─ 定时任务 ─────────────────────────────────┐
│  Cron: 每日凌晨                              │
│  ├─ 批量标签提取（全量用户）                  │
│  ├─ 质量评分（前一天完成的对话）              │
│  └─ 特征刷新（L1/L2 标签更新）               │
│                                              │
│  Cron: 每周                                  │
│  └─ 经验蒸馏（新增成交样本）                  │
└──────────────────────────────────────────────┘

┌─ 实时服务 ─────────────────────────────────┐
│  API: /api/strategy/{user_id}               │
│  ├─ 检查标签是否过期                         │
│  ├─ 过期则触发实时标签提取                   │
│  ├─ RAG 检索 + 策略生成                     │
│  └─ 返回策略卡片                             │
│                                              │
│  API: /api/quality/dashboard                │
│  └─ 从质量评分表聚合展示                     │
└──────────────────────────────────────────────┘
```
