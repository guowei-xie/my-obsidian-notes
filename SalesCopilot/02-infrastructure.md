# 数据基建与标签体系

---

## 标签体系

### 设计原则

标签分为两大类：**事实标签**（可观测、确定性的）和**推断标签**（AI 推理、概率性的）。

推断标签内部有严格的层次关系：**意向 = 话题 + 因素** — 意向不是独立判定的，而是从话题和因素中推导出来的。

```
事实标签（确定性）              推断标签（概率性）
┌─────────────────┐           ┌─────────────────────────────────┐
│  L1: 属性标签    │           │  L3: 推断标签（三层结构）        │
│  用户画像、渠道  │           │                                  │
│  来源于：数仓    │           │  ┌─ 话题层（在聊什么）           │
├─────────────────┤           │  │  学习情况、课程方案、价格...  │
│  L2: 行为标签    │           │  │                               │
│  埋点、履约数据  │           │  ├─ 因素层（信号是正是负）       │
│  来源于：埋点    │           │  │  每个话题下提取积极/消极因素  │
└─────────────────┘           │  │                               │
                              │  └─ 意向层（综合判定）           │
                              │     由话题×因素推导 → S0-S4      │
                              │                                  │
                              │  来源于：LLM                     │
                              │  需要置信度评分 / 定期更新       │
                              └─────────────────────────────────┘
```

**推导关系示例：**

```
对话中识别到的话题与因素:

  话题: 学习成绩
  └─ 积极因素: "孩子数学不错，很喜欢编程" → 学习兴趣

  话题: 课程了解
  └─ 积极因素: "你们这个课怎么报名？" → 主动询问

  话题: 时间安排
  └─ 消极因素: "周末排得太满了" → 时间冲突

综合推导:
  积极因素 2 个（学习兴趣 + 主动询问）> 消极因素 1 个（时间冲突）
  且出现了"报名询问"这一强购买信号
  → 意向判定: S3（需求明确），趋向 S4

这意味着：
  - 话题和因素是"证据层"，是 LLM 直接从对话中提取的
  - 意向是"结论层"，是基于证据综合推导的
  - 意向的每一次判定，都可以追溯到具体的话题×因素证据链
```

### L1: 属性标签（用户画像）

| 标签名 | 来源 | 示例值 | 更新频率 |
|--------|------|--------|---------|
| 城市层级 | 用户画像表 | 一线/新一线/二线/三线+ | 静态 |
| 年级 | 用户画像表 | 1-9 年级 | 按学期 |
| 渠道来源 | 订单表 | 抖音/微信/转介绍/自然流量 | 静态 |
| 设备类型 | 用户表 | iPad/PC/Mac | 首次登录 |
| Leads 评分 | Leads 模型 | 0-100 连续值 | 日更 |
| 是否复购 | 订单表 | 是/否 | 事件触发 |
| 来源直播间 | 订单表/渠道系统 | 直播间 ID + 主题 | 静态 |
| 直播间内容摘要 | 运营后台 | 直播主题、卖点关键词 | 静态 |
| 客服问卷结果 | 客服系统/CRM | 问卷填写内容 | 静态 |
| 客服沟通摘要 | 客服对话记录 | 初始诉求、关键信息 | 静态 |

### L2: 行为标签（埋点 + 履约）

| 标签名 | 来源 | 计算逻辑 | 更新频率 |
|--------|------|---------|---------|
| 体验课完课率 | 履约数据 | 完成课时 / 应到课时 | 课后 |
| 作品提交次数 | 埋点 | 学期内作品提交计数 | 日更 |
| 创作活跃度 | 埋点 | 近 7 天创作次数 | 日更 |
| 家长端活跃度 | 埋点 | 近 7 天家长端访问次数 | 日更 |
| 回复响应速度 | IM 记录 | 家长回复消息平均时长 | 日更 |
| 课堂互动频率 | 课堂数据 | 举手/连麦/答题次数 | 课后 |

### L3: 推断标签（AI 生成）— 三层结构

#### 第一层：话题（在聊什么）

从对话中识别出的沟通主题。话题是因素的"容器"。

| 话题 | 说明 | 示例对话 |
|------|------|---------|
| 学习情况 | 孩子的学业表现、学习习惯 | "孩子数学还不错" |
| 学习目标 | 学习的目的和期望 | "想提升逻辑思维" |
| 课程了解 | 对课程内容/形式的咨询 | "你们教什么语言？" |
| 课程体验 | 对已上课程的评价 | "孩子上完觉得挺有意思" |
| 价格费用 | 课程价格相关 | "这个课多少钱？" |
| 时间安排 | 上课时间、排课 | "周末时间排不过来" |
| 决策过程 | 谁来决定、怎么决定 | "我得和他爸商量一下" |
| 竞品比较 | 与其他机构对比 | "XX 机构也在看" |
| 孩子兴趣 | 孩子的态度和参与度 | "孩子挺喜欢的" |
| 比赛/考级 | 信奥、蓝桥杯等竞赛 | "什么时候能打比赛？" |

#### 第二层：因素（信号是正是负）

每个话题下提取的积极/消极信号。因素是意向的"证据"。

**积极因素（推动意向前进）：**

| 因素 | 关联话题 | 信号强度 |
|------|---------|---------|
| 学习兴趣 | 孩子兴趣、学习情况 | 中 |
| 目标明确 | 学习目标 | 强 |
| 主动询价 | 价格费用 | 强 |
| 主动约课 | 时间安排、课程了解 | 强 |
| 社交背书 | 课程了解 | 中 |
| 体验认可 | 课程体验 | 中 |
| 竞赛/升学需求 | 比赛/考级、学习目标 | 强 |
| 时间窗口明确 | 时间安排 | 中 |

**消极因素（阻碍意向推进）：**

| 因素 | 关联话题 | 化解难度 |
|------|---------|---------|
| 价格敏感 | 价格费用 | 中 |
| 决策权模糊 | 决策过程 | 中 |
| 时间冲突 | 时间安排 | 低 |
| 效果怀疑 | 课程体验、学习目标 | 高 |
| 兴趣不足 | 孩子兴趣 | 高 |
| 竞品倾向 | 竞品比较 | 高 |
| 年龄/阶段顾虑 | 学习情况 | 中 |
| 外部条件 | 其他 | 低 |

#### 第三层：意向（综合推导）

意向不是独立标注的，而是从话题×因素的组合中推导出来的。

| 阶段 | 推导逻辑 | 典型话题×因素组合 |
|------|---------|------------------|
| **S0** 暂缓/流失 | 明确拒绝信号，或消极因素压倒性主导 | 决策过程×"不需要" / 孩子兴趣×"不想学" |
| **S1** 沉默用户 | 无话题交集，或话题极少且无因素信号 | 无实质对话 / 仅"嗯""好的" |
| **S2** 需求模糊 | 有话题交集，有弱积极因素，但未形成明确方向 | 学习情况×"随便看看" / 课程了解×被动回应 |
| **S3** 需求明确 | 多话题下积极因素主导，主动表达需求 | 学习目标×目标明确 + 课程了解×主动咨询 |
| **S4** 强购买意愿 | 出现强购买信号（询价、约课、问报名） | 价格费用×主动询价 + 时间安排×主动约课 |

**推导规则（非穷举，LLM 综合判断）：**
```
- 强购买信号（主动询价/约课/问报名）出现 → 至少 S4
- 主动表达学习需求 + 无压倒性阻塞 → 至少 S3
- 有话题交互但无主动需求表达 → S2
- 无实质交互 → S1
- 明确拒绝或反复表达"不需要" → S0
- 任何阶段存在未化解的强阻塞因素 → 意向可能回退
```

#### 其他推断标签

| 标签名 | 来源 | 示例值 | 置信度要求 |
|--------|------|--------|-----------|
| 决策人角色 | 对话分析 | 母亲/父亲/祖辈/共同决策 | ≥ 0.5 |
| 竞品关注 | 对话分析 | 有/无 + 具体竞品 | ≥ 0.6 |

### 标签生命周期

```
创建: LLM 从对话/行为中提取
  ↓
存储: 写入推断标签表（含置信度、模型版本、原始证据）
  ↓
更新: 新对话发生时，重新推理并更新（保留历史版本）
  ↓
过期: 超过有效期（如 30 天无新数据）标记为 stale
  ↓
校验: 定期抽样人工校验，反馈给模型优化
```

## 数据流架构

### 全局数据流

```
┌──────────────────── 数据源层 ────────────────────┐
│                                                    │
│  用户画像表    行为埋点     对话数据    履约数据    │
│  (Hive)       (Sensors)   (API)      (Hive)      │
│                                                    │
└───────┬──────────┬──────────┬──────────┬──────────┘
        ↓          ↓          ↓          ↓
┌──────────────────── 采集层 ────────────────────────┐
│                                                     │
│  批量 ETL（日更）          近实时（按需触发）        │
│  ├─ 用户特征刷新           ├─ 对话数据拉取          │
│  ├─ 行为指标聚合           └─ 实时标签更新          │
│  └─ 履约数据同步                                    │
│                                                     │
└───────────────────────┬─────────────────────────────┘
                        ↓
┌──────────────────── 加工层 ────────────────────────┐
│                                                     │
│  标签计算                                           │
│  ├─ L1 属性标签 ← 用户画像 (SQL 直接映射)          │
│  ├─ L2 行为标签 ← 埋点聚合 (SQL 窗口函数)          │
│  └─ L3 推断标签 ← 对话文本 (LLM Agent)             │
│                                                     │
│  样本构建                                           │
│  ├─ User × Stage 维度的特征矩阵                    │
│  └─ 用于归因分析 & 模型训练                         │
│                                                     │
└───────────────────────┬─────────────────────────────┘
                        ↓
┌──────────────────── 存储层 ────────────────────────┐
│                                                     │
│  MySQL: 事实行为表、推断标签表、策略推荐表          │
│  Milvus: 对话向量（经验检索用）                     │
│  Redis: 热数据缓存（当前意向、策略卡片）            │
│                                                     │
└───────────────────────┬─────────────────────────────┘
                        ↓
┌──────────────────── 服务层 ────────────────────────┐
│                                                     │
│  销售端: 策略卡片 API（场景 1/3）                   │
│  管理端: 质量仪表盘 API（场景 2/4）                 │
│  分析端: 归因分析 API（场景 4）                     │
│                                                     │
└─────────────────────────────────────────────────────┘
```

## 建表结构

### 表 1: 事实行为表 `sales_copilot_fact_behavior`

记录用户行为事实（每条记录 = 一个行为事件）。

| 字段名 | 类型 | 含义 | 示例 |
|--------|------|------|------|
| `id` | BIGINT, PK | 自增主键 | |
| `user_id` | VARCHAR(32) | 用户 ID | |
| `class_id` | VARCHAR(32) | 班级 ID | |
| `counselor_id` | VARCHAR(32) | 课程顾问 ID | |
| `term_id` | VARCHAR(16) | 学期 ID | "2026spring" |
| `perform_stage` | ENUM | 履约阶段 | 见下方枚举 |
| `event_name` | VARCHAR(64) | 行为事件名称 | "call_made", "wechat_sent" |
| `event_time` | DATETIME | 事件发生时间 | |
| `event_source` | VARCHAR(32) | 事件来源 | "sensors", "im", "crm" |
| `event_metadata` | JSON | 事件附加信息 | `{"duration_sec": 180}` |
| `created_at` | DATETIME | 记录创建时间 | |

**`perform_stage` 枚举值：**
- `pre_first_class`: 进班至首课开始前
- `first_to_renewal`: 首课开始至续报开始前
- `renewal_period`: 续报开始后

**索引：** `(user_id, perform_stage, event_time)`, `(counselor_id, perform_stage)`

### 表 2: 推断标签表 `sales_copilot_inferred_tags`

AI 推理的用户标签（每条记录 = 一次推理结果的完整快照）。

| 字段名 | 类型 | 含义 | 示例 |
|--------|------|------|------|
| `id` | BIGINT, PK | 自增主键 | |
| `user_id` | VARCHAR(32) | 用户 ID | |
| `class_id` | VARCHAR(32) | 班级 ID | |
| `counselor_id` | VARCHAR(32) | 课程顾问 ID | |
| `term_id` | VARCHAR(16) | 学期 ID | |
| `perform_stage` | ENUM | 履约阶段 | 同上 |
| `topics_factors` | JSON | 话题×因素明细（证据层） | 见下方示例 |
| `positive_factors` | JSON | 积极因素汇总 | 见下方示例 |
| `negative_factors` | JSON | 消极因素汇总 | 见下方示例 |
| `customer_intention` | ENUM | 意向分类（结论层，由话题×因素推导） | "S0"-"S4" |
| `intention_reason` | TEXT | 意向推导理由 | |
| `confidence_score` | DECIMAL(3,2) | 整体置信度 | 0.85 |
| `model_version` | VARCHAR(32) | 模型版本 | "v1.0-qwen" |
| `source_dialogue_ids` | JSON | 源对话 ID | `["d_001", "d_002"]` |
| `inferred_at` | DATETIME | 推理时间 | |
| `expires_at` | DATETIME | 过期时间 | |
| `created_at` | DATETIME | 记录创建时间 | |

**`topics_factors` JSON 示例（证据层：话题×因素的完整推导链）：**
```json
[
  {
    "topic": "学习情况",
    "factors": [
      {"polarity": "positive", "tag": "学习兴趣", "proof": "孩子数学不错，很喜欢编程", "time": "2026-01-01 11:00"}
    ]
  },
  {
    "topic": "价格费用",
    "factors": [
      {"polarity": "positive", "tag": "主动询价", "proof": "这个课程多少钱？", "time": "2026-01-01 11:30"},
      {"polarity": "negative", "tag": "价格敏感", "proof": "感觉有点贵", "time": "2026-01-01 11:35"}
    ]
  },
  {
    "topic": "时间安排",
    "factors": [
      {"polarity": "negative", "tag": "时间冲突", "proof": "周末排得满满的", "time": "2026-01-01 12:00"}
    ]
  }
]
```

**`positive_factors` / `negative_factors` JSON 示例（从 topics_factors 中汇总提取）：**
```json
// positive_factors — 所有 polarity=positive 的因素汇总
[
  {"tag": "学习兴趣", "proof": "孩子数学不错，很喜欢编程", "time": "2026-01-01 11:00"},
  {"tag": "主动询价", "proof": "这个课程多少钱？", "time": "2026-01-01 11:30"}
]

// negative_factors — 所有 polarity=negative 的因素汇总
[
  {"tag": "价格敏感", "proof": "感觉有点贵", "time": "2026-01-01 11:35"},
  {"tag": "时间冲突", "proof": "周末排得满满的", "time": "2026-01-01 12:00"}
]

// intention_reason — 综合推导
// "用户在学习情况话题下表现出学习兴趣（积极），主动询问价格（强购买信号），
//  但同时存在价格敏感和时间冲突。综合判断：积极因素主导，有明确需求但存在可化解阻塞。"
// → customer_intention: S3（需求明确）
```

**索引：** `(user_id, perform_stage, inferred_at)`, `(counselor_id, perform_stage)`

## 样本构建

### 分析样本：User × Stage

用于归因分析和模型训练的宽表。

```
每条样本 = 一个用户在一个履约阶段的全部特征 + 结果

维度:
  - 用户特征: leads_score, grade, city_tier, channel, device_type
  - 状态特征: intent_stage, intent_change(Δ), days_in_stage
  - 行为特征: call_count, msg_count, class_completion_rate, creation_count
  - 服务特征: event_coverage, opportunity_utilization, objection_handling, service_depth
  - 结果: converted(0/1), renewal(0/1)
```

### 特征工程要点

| 特征类型 | 构建方式 | 注意事项 |
|---------|---------|---------|
| 用户特征 | 直接从画像表取 | 静态，无信息泄露风险 |
| 状态特征 | 从推断标签表聚合 | 需注意时间窗口，避免未来信息泄露 |
| 行为特征 | 从事实行为表聚合 | 按 perform_stage 分段聚合 |
| 服务特征 | 从关键事件表 + 信号响应表计算 | 需标准化处理 |
