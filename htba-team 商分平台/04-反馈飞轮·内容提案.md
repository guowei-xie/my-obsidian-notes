# 反馈飞轮 · 内容提案

> 子笔记，回链 [[00-总览]]。核心设计：**反馈不直接改资产**，中间用素材池缓冲、提案挂多份修订对比后择一合入。

## 全链路

```
客户端 data-collector 提炼候选变更（脱敏）
  → submit_feedback（batch_id 幂等）
  → 【反馈池 Feedback】status=new
       ├─ 整批采纳 accept / 整批忽略 reject
       ├─ 逐条 resolve（≥1 采纳入素材池，全忽略=整批忽略）
       └─ 退回重审 revert（已处理→new，关联 available 素材自动归档）
  → 采纳 → 【素材池 FeedbackMaterial】status=available（同一反馈至多一条 available，幂等）
  → 运营/skill propose → 【内容提案 ChangeProposal】target_kind 锁定一个资产，status=draft
       ├─ 加 revision（candidate 原稿 / agent 本地大模型 / human 运营手编）→ proposed
       ├─ select 选中一份 revision
       └─ apply → _write_target 写目标资产 + 重算 content_hash → merged（记 reviewer/merged_at + 写审计）
  → 素材标 consumed（consume_count+1，记 last_proposal_id）
  → 受影响角色包版本出红点 → 重组版本 → 发布（见 [[03-内容资产·角色包·三件套]]）
```

## 反馈池（Feedback）

表 `htba_team_feedback`（`models.py:311-339`）：`token_hash / user_label / role_pack_id / batch_id / candidates_json / candidate_decisions_json（逐条决策明细，仅 resolve 写）/ session_scenario / expected_outcome / status(new/accepted/rejected) / assignee`。

路由 `/feedback`（`routes/feedback.py`，受数据域过滤）：`GET ""` / `GET /{id}` / `POST /{id}/accept`（整批）/ `POST /{id}/reject`（整批）/ `POST /{id}/resolve`（逐条）/ `POST /{id}/revert`（退回重审）。

## 素材池（FeedbackMaterial）—— 关键缓冲层

表 `htba_team_feedback_materials`（`models.py:342-376`）：`source_feedback_id / batch_id / role_pack_id / candidates_json / session_scenario / expected_outcome / status(available/consumed/archived) / consume_count / last_consumed_at / last_proposal_id / archived_*`。

语义：审核通过的反馈沉淀成**可消费素材**，供 Agent/运营整理成提案；**同一反馈至多一条 available 素材**（幂等复用）；**可被多个提案复用**。路由 `/feedback-materials`：`GET` 列表/详情、`POST /{id}/propose`（推成提案，置 consumed）、`/archive`、`/restore`（有消费记录→consumed 否则→available）。

## 内容提案（ChangeProposal + Revisions）

**主表** `htba_team_change_proposals`（`models.py:427-473`）：`source_feedback / source_material_id / target_kind / target_code / kind(new/update) / summary / base_payload(现状快照) / status / selected_revision_id / reviewer / merged_at`。

`target_kind` **9 种**：`metric / method / sql_template / table_doc / system_prompt / workflow / role_pack_version / system_agent / role_pack_meta`。

**修订子表** `htba_team_change_proposal_revisions`（`models.py:476-495`）：`proposal_id / source(candidate/agent/human) / author / payload(JSON) / rationale / model_name`。三种来源：candidate=原稿、agent=本地大模型、human=运营手编。

**状态机** `draft → proposed → merged | rejected`：

- 直建即 `draft`；加 agent/human revision 后置 `proposed` 并把 `selected_revision_id` 指向它；merged/rejected 后不再接受新修订。
- **apply**（`change_proposal_svc.py:470-510`）：拒绝重复处理；**candidate 原稿不可直接合并**，必须先有 agent/human 修订；经 `scope_svc.ensure_can_land` 落地门槛（影响他人角色包的提案只能全量视角运营 apply）；`_write_target` 回写资产、置 merged、记 reviewer/merged_at、写 AuditLog。
- 特例：`role_pack_version` 提案 apply 调 `role_pack_svc.compose_version`（payload 用 `ComposeVersionReq` 校验，仅 `kind=new`）；`system_agent` apply 只创建 draft，release 仍需运营手工；`role_pack_meta` 只改 name/description。

> 注：不存在独立的 `role_pack_version_proposals` 表——角色包版本提案就是 `ChangeProposal.target_kind='role_pack_version'`。旧表 `content_prs`（0010）、`content_change_log`（0006）已删除。

## 飞书卡片双通道

- 发送记录表 `htba_team_feedback_lark_messages`（一接收人一行，含 `message_id / receiver_open_id`）；审批完成后按 feedback_id 反查全部 message_id 同步卡片状态，保证 web + 卡片双通道一致。
- 消费端 `services/lark_card_consumer.py`：WebSocket 长连接 daemon（lark-oapi SDK、私有 protobuf 帧），跨 loop 用 `run_coroutine_threadsafe` 回主 loop，3 秒死线兜底 toast；权限等价校验：open_id 反查 active AdminUser，超管全放行否则须含 `feedback.write`，数据域取 RolePackOperator 绑定。web 与卡片共用 `feedback_approval_svc`（web 传 `channel="admin_web"`）。

## 候选变更数据结构（PRD §5.6.4）

```yaml
batch_id: <ISO8601，幂等键>
source_session: <transcript_hash>   # 不含明文 transcript
target_role_pack: ops_analyst
candidate_changes:
  - id: C1
    category: sql_template          # metric | sql_template | method | table_doc | preference
    change_type: add                # add | modify | remove
    diff_or_new: |
      + SELECT channel, SUM(amount) ...
    risk: "channel 非分区字段，大表扫描需评估性能"
    user_confirmed: false
```

强制批次上下文（缺则后端 422）：`session_scenario`(≤2000) + `expected_outcome`(≤1000，须含可验证条件)。

## 运营 Skill（htba-team-operate）

管理端 skill，基于 admin REST 批量操作。**核心红线**：所有写动作一律走 `POST /change-proposals` + `/revisions`，**禁止**直接 CRUD 资产、**禁止**自动 apply/reject（人工签字）、**禁止**角色运营碰 system_agent/全局 system_prompt。鉴权用后台 PAT（`Authorization: Bearer`），第二步强制 `whoami` 确认角色域。四类能力：现状盘点 / 资料萃取成提案 / 素材池消费 / 提案审核辅助。
