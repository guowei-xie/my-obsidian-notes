# 图谱锚定评价与规则锚融合

> 子笔记 · 回链 [[00-总览]]。姊妹篇：[[01-实时语音全双工桥（火山 dialog 协议）]] · [[02-剧本生成与家长角色建模]] · [[04-方法论·可迁移模式]]
> 以代码 `@5a119d7` 为准。

## 核心命题：为什么不只让 LLM 打分

纯 LLM 打分有两个病：分数漂移（同样表现不同次分不一样）、无客观基准（"78 分"没法解释）。本项目的答案是**双轨融合**——LLM 给语义理解分（`llm_score`），Python 用图谱事实给客观锚分（`rule_score`），等权合成，并算出一个可解释的"你达到 Top 经验百分之几"的 `rule_anchor_score`。这是整个评价设计的灵魂（详见 [[04-方法论·可迁移模式]]）。

## 评价入口与降级（`src/pipeline/evaluator.py`）

`evaluate(config, script, transcript, custom_rubric, neo4j_client)`：
- transcript 为空 → 直接返回"待加强/对练为空"；
- 有 `neo4j_client` → 试 `_evaluate_v2`，**任何异常都 catch 并降级 v1**（`evaluator.py:64-68`）；
- 无 neo4j → `_evaluate_v1`。

**三级降级**：
1. 无 neo4j_client → v1；
2. v2 里检索全空（`not any(per_signal_methods.values())`）→ v1（`evaluator.py:130-132`）；
3. v2 运行抛异常 → v1。

v1 只跑 `prompts/evaluation_v1`，`drop_opportunities=True`（老 prompt 不认机会信号），只产 `objection_resolution`，`rule_anchor_score` 保持默认 0。

## v2 管线五步（`_evaluate_v2`）

1. **`_collect_signals`**：把 objections + opportunities 摊平成统一 signal 列表，每个带 `id/kind/title/content/level/mapped_factors`；
2. **`_retrieve_methods_parallel`**：`ThreadPoolExecutor`（并发度 `min(信号数, 8)`）对每个信号跑 `retrieve_for_signal`，返回 `{signal_id: [methods]}`；
3. **`build_reference_block`**：渲染成 prompt 友好的 markdown；
4. **LLM 评价**（deepseek-r1, temp 0.2）：`prompts/evaluation_v2` 输出每信号 `handled/llm_score/evidence/top_methods/matched_approach_ids/gap/advice`；
5. **`_assemble_result`**：LLM JSON + 规则锚分融合成 `EvaluationResult`。

## 逐信号图谱检索（`src/graph/signal_retriever.py`）

`retrieve_for_signal` 的检索策略（`signal_retriever.py:86-112`）：
- **objection** → `query_resolve`（查 `blocker_resolve` 类经验）；**opportunity** → `query_advance`（查 `intent_advance`/`pacing`/`context_leverage`）；
- **主查询用 `mapped_factors`**（剧本挂的图谱因素）；
- **主查询为空 → 用信号 title/content 抽关键词兜底**再查一次（`_keywords_from_text`：CJK 走 2-gram、英文/数字保留，去停用词，最多 8 个）；
- 结果 `_dedup`（按 approach_id）+ `_slim`（截断各长文本字段控制 token）后取 limit=5。

检索异常**吞掉返空列表**（不让图谱抖动打断评价）。

## Neo4j 只读查询（`src/graph/neo4j_client.py`，复用自 Strategy）

统一 `_RETURN_CLAUSE`：返回 Approach（id/name/description/example_count）+ Experience（execution_how/judgment_why/三段证据 before-action-after/from_stage/to_stage/factors_addressed），**`ORDER BY a.example_count DESC`**（Top 优先）。

- `query_resolve(keywords)`：`experience_type='blocker_resolve'` 且 `factors_addressed CONTAINS 关键词`（OR 拼接）；无关键词返 []；
- `query_advance(from_stage, factors)`：`experience_type IN [...]`，有因素时用 `CASE WHEN ... THEN 0 ELSE 1 END AS factor_priority` 把命中因素的经验**排前**（`ORDER BY factor_priority ASC, example_count DESC`）；
- `query_approach_detail(approach_id)`：取代表性最强一条，供前端 chip 点击展开（`/api/approaches/{id}`）；
- **注入防护**：`_sanitize` 用正则 `^[一-鿿\w]+$` 白名单过滤关键词，因为关键词被拼进 Cypher 字面量（`CONTAINS '...'`），不合规的 token 丢弃。

`CatalogCache`（`catalog_cache.py`）：线程安全、TTL 600s 的 {factors, topics} 缓存，`app.py` 启动时后台预热，剧本生成时消费。

## reference_block：跨信号去重防膨胀（`build_reference_block`）

多个信号可能检索到同一个 Approach，全展开会让 prompt 爆炸。策略（`signal_retriever.py:115-161`）：**同一 `approach_id` 只在首次出现处展开完整正文（方法说明/怎么做/为什么有效/三段证据），后续信号只写"详见信号 X 下 Top 方法 Y（同方法）"**。用一个 `seen_approach` dict 记录首现位置。这直接呼应 [[00-总览]] 提到的 `2691dd7` max_tokens 截断事故的根因治理。

## 规则锚分与融合（本项目最值得学的一段）

**`compute_rule_score`（`signal_retriever.py:164-180`）**——把"和 Top 比"变成数字：
```
coverage = Σ(命中的 candidate 的 example_count) / Σ(所有 candidate 的 example_count)
score    = clamp(round(1 + 4 * coverage), 1, 5)
candidates 为空 → 返回 0（信号：无数据，调用方据此回退到纯 LLM 分）
```
即：销售命中的方法在图谱里被越多真实经验支撑（example_count 越大），锚分越高。用 example_count 加权而非简单计数，是让"命中一个被 100 条经验验证的方法"比"命中一个只有 2 条的冷门方法"更值钱。

**融合（`_build_signal_item`，`evaluator.py:197-203`）**：
```
llm_score = clamp(LLM 输出, 1, 5)
rule_score = compute_rule_score(matched_ids, candidates)
score = rule_score>0 ? clamp(round(0.5*llm + 0.5*rule), 1, 5) : llm_score
```
`rule_score=0`（无候选/无数据）时**融合分回退到纯 LLM 分**，不让"图谱没数据"把分数拉低。

**防 LLM 幻觉**：`matched_approach_ids` 只保留在本信号候选集 `valid_ids` 内的 id（`evaluator.py:193-194`），LLM 编造的 approach_id 被丢弃。

**`rule_anchor_score`（`_assemble_result`，`evaluator.py:266-270`）**：只取 `rule_score>0` 的信号求均值 ×20（5 分制→100 分制）；全 0 则 0。这是结果页"与 Top 经验匹配度"进度条的数据源。

## 结果模型（`src/models/session.py`）

`EvaluationResult` 同时保留新旧两套字段：
- **新版** `signal_evaluation: [SignalEvalItem]`（含 llm/rule/融合三档分 + evidence + top_methods + candidate_methods 供前端 chip 跳详情 + gap + advice）+ `top_gap_summary` + `rule_anchor_score`；
- **旧版** `objection_resolution: [ObjectionEvalItem]`——由 `_signal_to_objection` 从新版异议信号转换而来，**兼容历史 session 与 v1 降级路径**。

这种"新字段并存 + 旧字段由新字段派生"是平滑演进的常见手法（v1→v2 不破坏历史数据）。

## 截断即失败（`src/llm/openai_chat.py`，git `2691dd7`）

`chat_completion_json` 拿到响应先看 `finish_reason`，`=='length'` 直接 `raise RuntimeError`（带 model + max_tokens 上下文），**不把残缺 JSON 喂给解析器**。此前的 bug 是：v2 输出字段多常超 3000 token 被硬截 → `JSONDecodeError` → 静默回退 v1 → `rule_anchor_score` 恒 0，不看日志难发现。治理三管齐下：max_tokens 3000→8000、截断显式 raise、prompt 加硬性长度上限（evaluation_v2/system.txt 尾段"输出长度硬性约束"）。
