# 方法论 · 可迁移的做法

> 子笔记 · 回 [[00-总览]]。本篇回答「这项目教会了我什么套路、能搬到哪去用」。执行器范式那一路已在 [[02-后端架构与执行器范式]]，这里聚焦调优方法本身。

## 模式一：把「Prompt 调优」重构成可收敛的评测循环

**问题原型**：任何「LLM + Prompt 做分类/判定/抽取」的场景，质量都卡在 Prompt，而 Prompt 靠人肉试错——没统一尺子、改坏说不清、无法复现。

**这个项目的解法**（可整套迁移）：把调优做成一个有明确收敛条件的循环——
`固定评测集 → 跑当前 Prompt → 按错例改写 → 再跑 → 比指标 → 循环到达标/轮次用尽`。
关键在于把循环里**每一环都工程化、去人肉化**：评测集是沉淀资产、改写是自动的、指标口径是固定的、达标是一个数（联合准确率 ≥ 阈值）。

**为什么值得搬**：它把「调 Prompt 要不要再改一版」这个凭感觉的判断，变成「离阈值还差多少、错在哪个类别」的可度量决策。任何要长期维护一个判定 Prompt 的团队都能复用这个骨架。

## 模式二：人只做二元裁决，机器占有全部机制

**取舍**：标注员的界面被刻意收窄到只回答「符合 / 不符合预期」+ 理由（正确答案选填），**不让人碰 Prompt、不碰指标口径、不碰模型参数**。

**为什么这么切**：
- 人擅长的是「这条判得对不对」的领域判断；不擅长、也不该被要求去写标准答案或调检索/Prompt。把界面收窄反而提高了标注吞吐与一致性（对上 [[00-总览]] 里 SONAR/Deka「机器占有机制、人占有判断」的同源思路）。
- 二元裁决 + 理由，是信息量最高又最省力的采集形态——它同时喂饱了下游两件事：多数票算「模型符合率」、理由原文喂给 AI 裁决与 Prompt 改写。

**迁移场景**：任何需要领域专家参与、但专家时间稀缺的 AI 质量评估——把专家的输入压到「二元判断 + 一句理由」，比让专家写标准答案更可扩展。

## 模式三：ground truth 用「三段式」产出，兼顾产能与质量闸门

标准验证集不是人直接写出来的，而是：
1. **符合直采**：多数票符合 → 直接采信模型输出（不调 LLM，省成本）。
2. **不符合/平票 → AI 推断**：调优模型结合人工理由在线推断建议答案（借 LLM 产能补齐人没写的标准答案）。
3. **推断必经人工复核**：所有 AI 推断条目一律 `needs_review`，人复核确认/修正后才进金标准；**且零待复核也要管理员显式确认**（人工质量闸门）。

**核心取舍**：明确拒绝「人填的正确答案直接进金标准」（v0.4 取消 `human_corrected` 直采）——因为个别错填会污染整个评测基准。宁可让人工答案只作 AI 推断的输入之一、再经复核把关。**这是「借 AI 提产能」与「守评测质量」之间一个考究的平衡点**，很值得在做任何「半自动构造标注集」时借鉴。

## 模式四：自动改写锚定「历史最优」而非「上一轮」，并用工程约束防横跳

AI 改写 Prompt 最容易翻车的地方是**指标反复横跳**：这一版改好了 category、改坏了 polarity，下一版又倒回去。项目的几个约束正是冲着这个：

- **基准锚定 best-so-far 轮**，不是紧邻上一轮——某轮变差不会污染后续改写的起点。
- **喂进改写模型的上下文是结构化的**：历史最优轮指标 + 错例按「标准值 → 模型值」方向分组 + 人工理由 + **历史轮修改记录**（明确要求「不要重复或回退此前改动」）。
- **硬约束改写动作**：必须保留占位符 `{dialogue_chunk}`；输出 JSON 的字段名/枚举取值与 Schema 完全一致、不得增删改；**优先做「定义澄清 / 类别边界规则 / 反例示例」级修改，禁止推倒重写**；每处修改要对应一个可见错误模式并写预期改善。
- **早停**：联合准确率连续 N 轮低于历史最优就提前终止，不浪费轮次。

**迁移价值**：这是一套「让 LLM 做梯度下降式优化」时防止发散的通用护栏——锚定最优、结构化反馈、约束动作幅度、记住历史别回退、设早停。做任何「AI 迭代优化 AI 产物」的循环都适用。

## 模式五：评测集升级为一等复用资产，是「可比」的前提

把验证集从「每个任务现攒的临时文件」升级为**标签级一等实体**（可跨调优任务引用），带来的不只是省事：
- 不同 Prompt 版本、不同调优任务，都在**同一把尺子**下比 → 指标才有可比性 → 调优才谈得上「收敛」。
- 配套「Prompt 版本链 + 每轮指标固化快照 + 迭代时间线」，让「第 3 次调优比第 1 次好在哪」可回溯。

**反面教训预防**：如果评测集每次重建，指标涨跌就分不清是 Prompt 变好了还是尺子变了。**任何迭代优化系统，先把评测基准钉死成可复用资产，再谈优化。**

## 模式六：把「越界输出」从硬失败降级为可观测信号

早期把「LLM 输出了 Schema 之外的枚举值」当作判定失败去重试。v0.4 改成：**解析成功但值越界 → 不失败，降级为 `schema_valid` 观测 + 统计遵从率**。

**取舍背后的想法**：越界本身正是「Prompt 没约束好模型」的**调优信号**，不该被丢弃或掩盖成失败。把它变成一个指标（Schema 遵从率），既留住了可用的判定结果，又把问题暴露给调优循环。**判断「什么该算失败、什么该算观测数据」，本身就是评测系统的设计决策**——默认把可利用的信号留下来。

## 一句话收束

这个仓库的价值密度，不在「又一个 React + FastAPI 后台」，而在两处编排智慧：**把人机分工切在正确的关节上**（人裁决、机器管评测与改写、AI 补产能、人守闸门），以及**把 AI 迭代优化 AI 的循环用工程约束框成收敛的**（锚定最优、结构化反馈、约束幅度、防横跳、早停）。这两套东西，脱离「价格意向打标」这个具体场景依然成立。
