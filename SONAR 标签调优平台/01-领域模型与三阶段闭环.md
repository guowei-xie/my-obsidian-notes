# 领域模型与三阶段闭环

> 子笔记 · 回 [[00-总览]]。本篇讲清「有哪些对象、怎么挂、状态怎么流转」。

## 对象层级

```
标签 Label (1)
 ├── Prompt 版本链 (N)          ← 标签级资产，v1→v2→…，每版记 source
 ├── 样本集 Sample Set (N)      ← 上传 CSV 落库，可复用
 ├── 验证集 Validation Set (N)  ← 一等实体，AI 裁决/上传生成，跨调优任务复用
 │    └── 验证集条目 Validation Item (N)
 └── 调优任务 Tuning Task (N)   ← label_id + seq_no，「第 N 次调优」
      ├── 判定运行 Judge Run (N)      ← purpose = initial / validation，不可独立创建
      │    └── 判定结果 Judge Result (N)  ← 与样本一一对应
      ├── 人工标注任务 Annotation Task
      │    └── 标注记录 Annotation (N)
      └── 调优轮次 Tuning Round (N)   ← 每轮：AI 改写 → 验证判定 → 内部比对
           └── 比对任务 + 比对明细/指标
```

**三条关键约束**（PRD §4）：
- 验证集归属**标签**而非调优任务，可被同标签下多个调优任务引用——这是「一次标注、跨任务复用」的结构基础。
- 判定运行、标注任务、调优轮次都必须挂在某个调优任务下；判定运行 v0.4 起不可独立创建/克隆（相关端点已删）。
- 所有对象**只可归档不可物理删除**（可追溯性要求）。

## 数据表（`slt_` 前缀，MySQL bitest 库）

业务库是线上共享库，所有表统一 `slt_` 前缀作业务隔离；Alembic 只管理 `slt_` 表（版本表 `slt_alembic_version`）。核心表：

| 表 | 承载 | 关键字段 |
|---|---|---|
| `slt_labels` | 标签 | `name` UK、`sonar_session_id` UK、`sonar_query`、`sonar_meta_json`（原始 JSON 存档，只读） |
| `slt_prompts` | Prompt 版本链 | `label_id`、`version`、`content`、`source`、`change_note` |
| `slt_model_providers` | 模型端点 | `base_url`、`api_key_encrypted`（后端加密，前端不回显）、`enabled` |
| `slt_sample_sets` / `slt_samples` | 样本集/样本 | 正文 `original_content MEDIUMTEXT` 独立存、结果表只存外键（承载 30 万行级） |
| `slt_tuning_tasks` | 调优任务 | 双模型字段（judge_* / tuning_*）、`output_schema_json`、`target_metrics`、`status`、`best_round_id`、`best_prompt_id`、`report_json` |
| `slt_tuning_rounds` | 调优轮次（即断点） | `round_no`、`prompt_id`、`status(rewriting→judging→comparing→done/failed)`、`metrics_json` |
| `slt_judge_tasks` | 判定运行 | `tuning_task_id`、`purpose(initial/validation)`、`progress_json`、`stats_json` |
| `slt_judge_results` | 判定结果 | `raw_output`、`parsed_json`、`status`、`schema_valid`、`retry_count`、`tokens_json` |
| `slt_validation_sets` / `slt_validation_items` | 验证集/条目 | 条目 `source`、`needs_review`、`answer_json` |
| `slt_annotation_tasks` / `slt_annotations` / `slt_annotation_locks` | 标注 | 标注 `UNIQUE(task, sample, user)` 兜底防重；锁表做分发并发防重 |
| `slt_compare_tasks` / `slt_compare_details` | 内部比对 | 引用 `validation_set_id / tuning_round_id`（不再上传文件） |
| `slt_audit_logs` / `slt_exports` | 审计 / 导出 | 全量留痕、下载历史 |

**设计要点**：多选字段的值在所有 `*_json`（`parsed_json / answer_json / standard_json / correct_answer_json`）里统一为 JSON 数组；报告/指标一律固化为 `report_json / metrics_json`，避免历史报告随代码口径变化漂移。

## 三阶段状态机

```
draft → s1_judging → s1_done
      → s2_annotating → s2_annotated → s2_adjudicating → s2_reviewing
      → s3_ready ⇄ s3_running ⇄ s3_paused
      → completed / canceled
```

创建任务时若上传验证集文件或引用就绪验证集 → **跳过 s1/s2 直达 `s3_ready`**。

### 阶段 1 · 初判（s1_*）

- 「开始初判」创建 `purpose=initial` 判定运行，复用判定执行器：asyncio 并发调用 LLM，逐条把 `original_content` 注入 `{dialogue_chunk}`。
- **Schema 校验策略（v0.4 关键调整）**：解析成功但字段值越界的输出**不重试、不判失败**，降级为 `schema_valid` 观测并统计**Schema 遵从率**；只有 JSON 解析失败/调用失败才按重试策略处理（≤ N 次仍失败标 `failed` 并保留原始返回）。
  - *为什么*：早期把「越界」当失败会导致明明能用的判定被丢弃、且掩盖了「Prompt 让模型产出越界值」这一真正要调优的信号——把它变成可观测指标而非硬失败，才对得上调优目的。

### 阶段 2 · 标注与验证集（s2_*）

**（上）人工标注**——两种分发规则（`annotation.py`）：
- **优先凑票制**（目标票数 V ∈ {3,5,7}）：按 `v(s)` 降序（越接近 V 越优先），集中火力让样本尽快凑满、产出多数票结论；全部达 V 自动结束。
- **均匀得票制**（上限 M 可空）：按 `v(s)` 升序（票少者优先）；设 M 则达 M 退出分发，不设 M 只能手动结束。
- 硬约束：同一员对同一样本仅一票（DB 唯一键 + 分发过滤）；样本推送后短时锁定（如 10 分钟），超时释放回池不计票；**不允许跳过**。

**结束后固化评价报告**：主指标「模型符合率」（多数票为符合的样本 / 已裁决样本），辅以全票一致符合率、覆盖率、分字段/分枚举值符合率（定位薄弱类别）、标注员间一致率（样本量够补 Fleiss' κ）、不符合理由列表（喂给下游裁决与改写）。

**（下）AI 裁决生成验证集**（`adjudication.py`）——管理员触发「生成验证集」后：

| 情形 | 处理 | 条目 source |
|---|---|---|
| 多数票「符合」 | 直采模型输出（不调 LLM）；模型输出本身越界则转复核 | `model_confirmed` |
| 多数票「不符合」或平票 | 记 pending，调优模型结合标注理由（含票中「正确答案应为」，作推断上下文而非直采）在线推断 | `inferred` |
| 全部 inferred 条目 | 一律 `needs_review` 进人工复核，修正后 | `human_reviewed` |

> **v0.4 定稿口径**：人工填的「正确答案应为」不再确定性直采（`human_corrected` 路径取消，仅历史遗留保留）——人工答案只作推断输入之一，最终经人工复核把关，避免个别错填答案直接进金标准。
>
> **人工质量闸门**：裁决后**恒进入** `s2_reviewing`，即便零待复核条目也需管理员显式「确认生成」验证集才置就绪、任务进 `s3_ready`。

### 阶段 3 · 迭代调优（s3_*）

引擎循环（详见 [[02-后端架构与执行器范式]]）：
1. **round 0 基线轮**：直接以初始 Prompt 对验证集全量判定评测。
2. 未达标 → **AI 改写 Prompt**（调优模型），基准锚定**历史最优轮**（best-so-far，非上一轮）。
3. 新 Prompt 自动落版本（`source=tuning_ai`）→ 创建 `purpose=validation` 判定运行，对验证集全量判定。
4. **内部比对**：判定结果与验证集逐字段比对。
5. 达标 / 轮次用尽 / **早停**（联合准确率连续 N 轮低于历史最优，N 默认 2、可配 `[tuning] early_stop_patience`、0 关闭）→ 固化最优轮 + 迭代报告 → `completed`。

**目标指标**：联合准确率 ≥ 阈值（默认 0.9）+ 单次最大改写轮次（默认 5、上限 20）。

**人工干预**：可暂停/取消；暂停后可指定**基准 Prompt** 恢复（该轮跳过 AI 改写直接评测）；改写连续产不合法 Prompt → 本轮 failed、任务转 `s3_paused` 等人工处理；**终态续轮**——completed/canceled 任务可在末轮之后就地追加轮次重开（不新建任务，累计总轮数可超 20，已达标需先提阈值）。

## 比对指标双口径

**单选字段**：字段准确率、混淆矩阵（标准值×模型值，定位「谁被误判成谁」）、分类别 P/R/F1 + macro。
**多选字段**（值为枚举集合，混淆矩阵不适用）：严格匹配率（主指标，集合完全一致占比）、平均 Jaccard、值级 P/R/F1（每个枚举值当独立二分类）、值级漏标(FN)/多标(FP)条形图。
**跨字段汇总**：联合准确率（所有枚举字段全对占比）= 达标判据；错误明细逐字段列差异。
