# SONAR 标签调优平台

> 项目入口笔记（八段概览）。技术深挖见子笔记：[[01-领域模型与三阶段闭环]] · [[02-后端架构与执行器范式]] · [[03-方法论·可迁移模式]]

## 一句话是什么

SONAR 标签调优平台（sonar-label-tuning，表前缀 `slt_`）是一个**判定 Prompt 的调优流水线**：在上游 SONAR 检索平台初筛出的对话片段之上，叠加一层「LLM + Prompt」的分类判定，并用一个三阶段闭环——**初判 → 人工标注沉淀标准验证集 → 全自动迭代改写 Prompt**——持续把判定 Prompt 打磨到达标。核心单元是「调优任务」（一个标签下的「第 N 次调优」），核心资产是「标签级验证集」（一次标注沉淀、跨任务复用的 ground truth）。

## 场景叙事与价值

**上游痛点**：SONAR（原 [[00-总览|Deka]] 检索对齐工作台）通过语义召回，从海量「家长-老师」对话里初筛出与某主题相关的片段（chunk）。以「价格意向」为例，一次会话召回约 30 万个 chunk，阈值处 precision ≈ 0.83——**够用但不够好**：有误召回，且不能给出业务要的细分类别与意向极性（如 category 七选一、polarity 四选一）。所以要在初筛之上再叠一层 LLM 判定。

**真正的痛点在闭环缺失**：判定质量由 Prompt 决定，Prompt 要靠反馈反复迭代。而「判定 → 评估 → 调优 → 再判定」这个循环，原来是人肉的：跑一批、抽样看、凭感觉改 Prompt、再跑一批——没有统一的评测口径、没有标准答案沉淀、没有版本可追溯、改坏了也说不清。这个平台把整个循环工程化、平台化。

**分工重构是价值核心**：平台把调优拆成「人只擅长的部分」和「机器该干的部分」——
- **人只做裁决**：标注员对一条判定结果只回答「符合 / 不符合预期」（+ 理由，可选正确答案）；不碰 Prompt、不碰指标口径。
- **机器管全部机制**：批量判定执行、多数票裁决、AI 在线推断标准答案、按错例自动改写 Prompt、内部比对算指标、循环到联合准确率达标或轮次用尽——全自动，且全程可人工暂停/指定基准/续轮干预。

**没有它 vs 有了它**：

| 维度 | 没有它 | 有了它 |
|---|---|---|
| 评测口径 | 每次抽样凭感觉，口径不统一 | 一次标注沉淀成标签级标准验证集，之后所有轮次统一以验证集内部比对为准 |
| 改 Prompt | 人肉试错，改坏说不清 | 迭代引擎按错例分组自动改写 + 自动落版本，锚定历史最优轮防横跳 |
| 覆盖与规模 | 人一次只能看几十条 | asyncio 执行器批量判定数千~数万条，断点续跑、失败重跑 |
| 可追溯 | Prompt/参数/结果散落，历史漂移 | Prompt 版本链 + 每轮指标固化快照 + 迭代时间线 + 操作审计 |

## 核心功能逻辑

平台围绕**一个层级模型**和**一台状态机**运转（详见 [[01-领域模型与三阶段闭环]]）：

- **顶层是标签（Label）**：业务判定主题（如「价格意向」），定义只读、解析自 SONAR 导出的 `metadata.json`。标签下挂四类**标签级资产**：Prompt 版本链、样本集、验证集、调优任务。
- **核心单元是调优任务（Tuning Task）**：`label_id + seq_no`（「第 N 次调优」），走一条三阶段状态机：
  `draft → s1_judging → s1_done → s2_annotating → s2_annotated → s2_adjudicating → s2_reviewing → s3_ready ⇄ s3_running ⇄ s3_paused → completed/canceled`。
  - **阶段 1 初判**：判定模型对样本集批量判定（一次「判定运行 Judge Run」），逐条把 `original_content` 注入 Prompt 占位符 `{dialogue_chunk}`，输出按 Schema 解析。
  - **阶段 2 标注与验证集**：对初判结果发起人工标注（凑票制 / 均匀得票制分发）→ 多数票裁决 → **AI 裁决在线生成验证集**（符合直采模型输出、不符合/平票由调优模型按理由在线推断）→ 全部推断条目进人工复核 → 管理员显式确认，验证集置就绪。
  - **阶段 3 迭代调优**：验证集就绪后启动迭代引擎——round 0 基线评测 → 未达标则**调优模型按错例自动改写 Prompt**（自动落版本 source=`tuning_ai`）→ 新版本对验证集全量判定 → 内部比对算指标 → 循环，直到联合准确率达标 / 轮次用尽 / 早停 → 固化最优轮 + 迭代报告。
- **两套模型分离**：判定模型（judge，跑初判与每轮验证判定）与调优模型（tuning，跑裁决推断与 Prompt 改写）独立配置，调优模型可留空默认沿用判定模型。
- **指标双口径**：单选字段用准确率/混淆矩阵/PRF1，多选字段用严格匹配率/Jaccard/值级 PRF1，跨字段汇总为「联合准确率」（所有枚举字段全对的样本占比），即达标判据。

技术栈：后端 FastAPI + SQLAlchemy + Alembic + OpenAI 兼容 SDK（Python ≥ 3.12，uv 管理）；前端 React 19 + Vite + Antd 6 + react-router 7；业务库线上 MySQL（bitest 库，`slt_` 前缀），本地开发默认 SQLite。

## 方法论 · 可迁移的做法

一句话：**这个项目教的是「怎么把一个 LLM Prompt 的调优，从手艺变成可收敛的工程流水线」，以及「怎么把长时后台作业做成崩了能自己爬起来的执行器」。** 三条最值得搬走的模式（展开见 [[03-方法论·可迁移模式]]）：

1. **人机分工的调优 harness**：把「判断」与「机制」彻底切开——人只回答二元裁决 + 理由，机器占有评测口径与 Prompt 改写。评测的 ground truth 不是人直接写的答案，而是「人裁决 → AI 按裁决理由推断 → 人复核把关」三段式产出，既借了 LLM 的产能又留了人工质量闸门。
2. **验证集作为一等复用资产**：评测标准从「每次现攒」升级为「标签级实体，一次沉淀、跨任务复用」，让不同 Prompt 版本、不同调优任务在**同一把尺子**下可比——这是调优能收敛的前提。
3. **自动改写锚定「历史最优」而非「上一轮」**：AI 改写 Prompt 时，基准是 best-so-far 轮而非紧邻上一轮，喂进去的是错例按「标准值→模型值」方向的分组 + 人工理由 + 历史修改记录，并硬约束「保留占位符、Schema 不得增删改、只做定义澄清/边界/反例级修改、别回退历史改动」——用工程约束防止迭代反复横跳。

配套还有一套**执行器范式**：库表状态即断点（`slt_tuning_rounds` 的 `rewriting→judging→comparing→done`、`slt_judge_results` 的逐条明细），进程重启按未完成明细幂等续跑；进程内注册表做并发/暂停/取消控制，因此**强约束单 worker 部署**并用文件锁兜底。

## 关键概念与术语表

| 术语 | 含义 |
|---|---|
| SONAR / Deka | 上游语义检索平台，初筛出主题相关对话片段（chunk）；本平台在其产物上叠加判定 |
| 标签 Label | 业务判定主题，平台顶层组织单元；定义只读、解析自 `metadata.json` |
| 调优任务 Tuning Task | 标签下一次完整调优（`label_id + seq_no`，「第 N 次调优」），贯穿三阶段生命周期 |
| 判定运行 Judge Run | 调优任务内部一次 LLM 批量判定；`purpose`：`initial`（初判）/ `validation`（每轮验证）；不再独立创建 |
| 输出 Schema | 结构化输出定义：字段名 + 类型（枚举单选/多选/文本）+ 枚举取值；用于解析校验与指标计算，支持 AI 生成 |
| schema_valid | Schema 遵从观测标记：字段值越界的输出不判失败，降级为观测并统计遵从率 |
| 票 / 标注 | 一个标注员对一个样本的一次「符合/不符合 + 理由」；同一员对同一样本仅一票 |
| 凑票制 / 均匀得票制 | 两种分发：凑票制优先让样本尽快凑满目标票数（3/5/7）；均匀制票少者优先 |
| AI 裁决 Adjudication | 标注结束后在线生成验证集：符合直采（model_confirmed）、不符合/平票由调优模型推断（inferred）后必经人工复核（human_reviewed） |
| 验证集 Validation Set | 标签下一等实体，作为比对 ground truth，可跨调优任务复用 |
| 调优轮次 Tuning Round | 阶段 3 一轮：AI 改写→验证判定→内部比对；round 0 为基线轮 |
| 内部比对 Compare | 某轮验证判定结果与验证集逐字段比对（引用 `validation_set_id / tuning_round_id`） |
| 联合准确率 | 所有枚举字段全对的样本占比，阶段 3 达标判据（默认阈值 0.9） |
| 判定模型 / 调优模型 | 判定模型跑初判+验证判定；调优模型跑裁决推断+Prompt 改写；后者可留空沿用前者 |

## 上手 / 使用路径

**读代码路径**（想看懂实现）：
1. `docs/PRD.md`（v0.4）——最完整的产品与数据模型说明，先读它。
2. `backend/app/models/`——`slt_` 全量数据模型，对照 PRD §8 看层级。
3. `backend/app/services/`——业务核心：`judge_executor.py`（判定执行器）、`tuning_executor.py`（迭代引擎）、`adjudication.py`（AI 裁决）、`prompt_rewrite.py`（改写）、`compare.py`（比对指标）、`annotation.py`（标注分发/评价，最大文件 803 行）。
4. `backend/app/main.py`——看 `lifespan` 里的执行器单进程锁与四个 `resume_*` 恢复钩子。
5. `frontend/src/routes.tsx`——页面地图；`pages/` 下按 labels/tuning/annotation/judge/compare/admin 分目录。

**跑起来**（本地开发）：
```bash
./scripts/dev.sh              # 一键：端口从 backend/config.ini [server] 段读取（默认 8000/5173）
# 或手动：
cd backend && cp config.ini.example config.ini && uv sync && uv run alembic upgrade head \
  && uv run uvicorn app.main:app --reload --port 8000     # 默认 sqlite 本地库
cd frontend && npm install && npm run dev                  # 5173，/api 代理到 8000
```

**用起来**（业务闭环）：建标签（传 `metadata.json`）→ 建调优任务（选判定/调优模型 + Prompt + 样本集 + 输出 Schema + 目标指标）→ 开始初判 → 发起人工标注 → 生成验证集 + 复核确认 → 启动迭代调优 → 看迭代报告固化最优 Prompt。想跳过前两阶段可在建任务时直接上传/引用就绪验证集直达 `s3_ready`。
