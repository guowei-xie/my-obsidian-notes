## 1. 里程碑

### M0（2 周）— 原型走通

**目标**：用一个真实角色 + 一张真实表，端到端跑通"提问 → MCP → SQL → 返回"。

交付物：
- [ ] MCP 网关骨架（FastAPI + `mcp` SDK + sqlglot AST 校验）
- [ ] 1 个硬编码角色包（不走后台，配置写在网关本地）
- [ ] 插件薄壳（SessionStart hook + MCP 配置 + token-set 命令）
- [ ] 个人习惯文件 `preferences.md` 注入机制
- [ ] 业务 MySQL 只读账号 + 1 张测试表

验证：
- 1 名内测用户用 token 完成一次完整查询
- 越权 SQL（查未授权表）被拒绝且写入 audit_log

### M1（4 周）— MVP 上线

**目标**：后台最小可用，3 个角色正式上线。

交付物：
- [ ] 管理后台（FastAPI + 极简前端）
  - Token 录单 + 吊销
  - 表元数据探索 + 字段补全
  - 内容仓库（skill / SQL 模板 / 口径）版本化编辑
  - 角色包编排
- [ ] `data-collector` Agent v1（识别 Q/B/E + 用户征询 + 本地脱敏）
- [ ] 反馈池基础视图
- [ ] 3 个角色包（用户增长 / 教研 / 续费）

验证：
- 3 个角色各 ≥3 名真实用户接入
- 一周内反馈池有 ≥10 条上报，至少 3 条转为内容更新

### M2（4 周）— V1 完整闭环

**目标**：可灰度、可审计、可回滚。

交付物：
- [ ] 灰度发布（按 token 白名单 / 比例）+ 一键回滚
- [ ] 审计中心查询界面
- [ ] 监控看板（调用量、成功率、采纳率）
- [ ] 每月反馈采纳报告自动生成
- [ ] 双人审核流强制化（生产环境）

验证：
- 至少完成一次"灰度 20% → 全量"的真实发布
- 触发一次回滚演练

### M3（持续）— 演进

- 口径回溯查询（按时间点查询当时口径）
- 报告自动归档与版本固化
- 跨角色协同（用户增长 + 续费联合分析）
- 智能补全 preferences.md 的建议质量提升

## 2. 开放问题（需要用户/相关方确认）

| # | 问题 | 影响里程碑 | 建议解法 |
|---|------|-----------|----------|
| 1 | 产品正式名称（目前用「商分团队插件」占位） | M0 | 用户定一个英文 code 与中文名（用于 plugin.json 与目录） |
| 2 | 业务 MySQL **只读账号**的申请流程与连接信息 | M0 必需 | 沿用公司常规 DBA 申请流程；账号最小权限：`SELECT` only，且仅授指定 schema |
| 3 | 平台元数据库（`bizanalyst_meta` schema）部署位置 | M0 | 建议 M0 阶段与业务库同实例不同 schema，M2 后再考虑独立实例 |
| 4 | 管理后台的访问入口与登录方案 | M1 | 内网域名 + 内部 SSO；若公司无统一 SSO，先用简单口令 + IP 白名单 |
| 5 | Token 默认有效期 | M0 | 建议 90 天；敏感角色可配置为 30 天 |
| 6 | 脱敏规则是否需要法务/合规预审 | M1 | 建议 M1 上线前送一版给合规过目 |
| 7 | 灰度回滚的责任人与决策机制 | M2 | 产品 + 数据负责人 + 安全各一名作为 RACI 中的 A/C |

## 3. 风险与依赖

| 风险 | 影响 | 缓解 |
|------|------|------|
| 业务 MySQL 只读账号下不来 | 阻塞 M0 | 提前 1 周走 DBA 流程；M0 可用脱敏后的测试库先跑通链路 |
| 商分专家无暇沉淀 skill / SQL 模板 | 阻塞 M1 内容上线 | 第一版由实施同学陪同抽 3-5 个核心场景结对完成 |
| 用户对采集 agent 询问感到打扰 | 影响留存 | 默认低频；提供"本周不再提示"开关 |
| 灰度期口径不一致引发误读 | 数据可信度 | 报告固化口径版本号；灰度期 UI 显式提示 |

## 4. 不在本期范围

明确**不做**的事，避免范围蔓延：

- 不做 OA 系统对接（运营手工录单足够）
- 不做用户身份系统（用 token + user_label 即可）
- 不做可视化报表渲染（结果以表格形式返回，可视化由用户自有 BI 完成）
- 不做跨语言 SDK（只有 Claude Code 插件这一种客户端）
- 不做权限申请自助化（仍走 OA）
